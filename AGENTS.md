# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Checks: `npm run check` (tsc, strict) and `./crewhouse test` (a throwaway HOME, then a check that the owner's `~/.pi` sign-ins, settings and extensions are byte-for-byte unchanged). Run both before committing; CI (`.github/workflows/ci.yml`) runs them plus the web build on Node 22.22.3 (OpenClaw's floor) and 24, so tests must never need an account, the network or a model: crew-logic tests run on the scripted `StubRuntime` (`src/stub-runtime.ts`, `CREWHOUSE_ENGINE=stub`; the script is in the file header), and the pinned Gateway's own tests run on the scripted HTTP provider (`test/openclaw-stub.ts`).
- Tests wait on a condition with a bound, never a fixed sleep: CI's disks are slow. This holds for a sleep you judge safe (a short one, or one waiting out a lifetime) and for sleeps already on main — a CI flake you traced to a fixed sleep is yours to convert, not to explain away. Use `test/lab.ts` (`setup`, `until`, `settled`, `holding`, `release`); daemon tests take an OS-assigned port.
- Node runs `src/*.ts` directly with type stripping: no parameter properties, enums or namespaces (tsconfig sets `erasableSyntaxOnly`). Imports use `.ts` extensions.
- Size budget: crewd (`src/`) stays at or under 6,949 lines, measured after the dead-routing deletion and enforced by `test/line-budget.test.ts`: every change keeps src/ net <= 0, and raising the number needs an owner decision. Prefer deleting to adding.
- The engine is OpenClaw, driven through the BYOKit OpenClaw kit (`@byokit/openclaw`, pinned exactly on npm). The kit owns the supervised child (env built from nothing: loopback bind, token auth, channels/Control UI/Tailscale/mDNS off), transport, sign-in wizard, runs, bridge plugin, engine installation (`prepare()`) and install policy; `src/openclaw/runtime.ts` is the only file that imports it (maps members to `m<id>` and Crewhouse's `bash` to the model-visible `shell` — the engine rewrites a tool called bash to its own exec — and holds the tool schemas, Crewhouse's engine config and trusted skill list) — `test/openclaw-bridge.test.ts` fails otherwise, and exercises the kit's isolated `prepare()` installer; production uses `runtime/openclaw` (the kit's `engineDir`); the kit's published `engine/` pin is authoritative, with no committed mirror. A kit gap goes to the BYOKit repo, never a Crewhouse-side patch; `test/kit-fake.ts` runs the port on the kit's fake Gateway. Tasks are sessions keyed `agent:m<member>:crewhouse:<bot>:<task>` (stored in `tasks.session`); a resume continues the same key. Account coverage follows OpenClaw's supported subscription routes (spec §12 of data/ch-openclaw-found/spec.md); the pin-bound matrix lands with the sign-in step. Bump OpenClaw deliberately: `test/openclaw*.test.ts` (isolation, loopback, fail-closed gate) plus the stub suite are the gate.
- Sign-in goes through the engine's own wizard (`runtime.signIn`); `src/accounts.ts` is the person-facing shim: who is signed in (`ready`, keyed `<member>:<account>`), the sign-in card view, and the states the product words come from (`expired`, `excluded` for a plan without helpers, `rests` for cooldowns). `classify` (`@byokit/accounts`) maps an engine error to those states. The kit listens on ChatGPT's fixed port 1455 (`CREWHOUSE_CALLBACK_PORT` in tests) during a browser sign-in (the redirect lands there); the device code is the fallback. The wizard hands over steps only when pulled with `wizard.next` — `wizard.status` answers `{status, error}` and never carries a step — and the engine admits one setup session at a time, so the kit cancels its own session with `wizard.cancel` on every exit short of done (test/openclaw-wizard.test.ts pins this on the real engine). The fs tracer the isolation test uses is in-repo: `test/trace-fs.mjs`.
- The upgrade migration (`runtime.migrate` + `confirm`, `test/openclaw-migrate.test.ts`) is staged and witnessed: the engine installs before doctor runs, doctor only runs while no gateway owns the state dir (the engine enforces this), its exit code is a weak yes, and a member's old auth is retired (renamed) only after `models.authStatus` reports the sign-in. Stage legacy `auth.json` inside `auth-profiles.json` so doctor canonicalizes `openai-codex` to `openai` before SQLite import; already-retired originals can be repaired the same way. A failed import leaves the original in place; the next boot retries. The app's account list (`AIS` in `web/src/adapter.ts`) must match `PROVIDERS` in `src/accounts.ts` — `test/ui.test.ts` pins the keys; screen sources (.tsx) must not contain the word `claude` literally (scan at test/ui.test.ts), so account names/colours live in the adapter and their marks in `web/src/logos.ts` (the phone's PNGs come from it via `node scripts/icons.mjs`; `mobile/src/marks.ts` holds the requires).
- Finished files a model specs and crewd writes: spreadsheets `src/workbooks.ts` (`crew_workbook`, exceljs pinned exactly in `package.json`; `test/workbooks.test.ts` is the gate) and documents `src/documents.ts` (`crew_document`, docx pinned, read back through its own jszip/xml-js; `test/documents.test.ts`). The helper hands over a plain spec, the model never hand-writes the binary, and the app renders only crewd's JSON (`GET /api/workbook`, `GET /api/document`, delivered-to-member checked) — never the file. One card + one read-only panel serve both (web/src/parts.tsx `PreviewCard`/`PreviewPanel`).
- Policy is `src/policy.ts` `effectOf`, called from the engine's `tool_call` hook (`Crew.gate`): unknown tools fail closed. Work in the bot's space and the bubblewrap shell never asks; spending never gets a standing answer (its effect has no `key`). A press on a site the person signed the bot in to is a `send` with no `key` either, so it asks every time and its card names the button and the money read from the page's own snapshot (`policy.pressOf`, `Crew.press`) — never the model's description of what it is about to do. A claim form's lines are the family's own words: where the person signed the bot in, each line asks on its own card as `label: value`; a form the helper typed lines into asks its submit on any host, signed in or not, and that card lists every line. Card words come from the tool and its input, never the model. A job whose call acted out in the world (`policy.acts`) ends `done` only after `crew_outcome {worked: true}`; otherwise `unsure`, with a line and an alert like a failure. Likewise a delivered `*.patch` counts only after crewd's own `crew_verify` saw its check fail on the base and pass with it (both runs in the bot's sandbox; the exit codes are crewd's; each worktree is seeded with a copy of the bot's installed `node_modules`, and a before side that failed on a missing module is marked `missingDep` and never counts). A draft in the person's name goes on a `crew_draft` card that records approve or reject; nothing is sent either way. `scripts/validate-support.mjs <task>` checks a support run against crewd's own `run.call` record and events, never the helper's word. Command-line tools needing the person's sign-in are typed host tools (`run.free`/`run.spend` in `tools/<id>/tool.json`), never shell.
- Tool kit: manifests in `tools/*/tool.json`, logic in `src/tools.ts` (`resolveGrants`, `installTool`). Tests set `CREWHOUSE_TOOLS_DIR` to a temp dir; a real `./crewhouse tools install` downloads Chromium (~170 MB). A pinned tool never resolves from the owner's PATH; with a `package-lock.json` beside its manifest it installs by `npm ci`, scripts off. Agent-facing tools prefer AXIs (https://axi.md) over MCP: one `args` schema per tool, not a server's dozens every turn. An AXI runs by absolute path on crewd's node with `axiEnv` (the bot's own HOME and every XDG dir: `XDG_CACHE_HOME` beats HOME), never `process.env`; `test/isolation.test.ts` checks the owner's whole HOME stays byte for byte.
- Which account a task runs on is picked in `src/crew.ts` `run()`: its own `brain` first, then the bot's `models` in `bot.json` (keys of `PROVIDERS` in `src/accounts.ts`), skipping resting, signed-out and plan-less ones (`usable`). A failed turn's `RunEnd` kind does the old failover: the account rests or is flagged, the task requeues with a handoff line, and the same session key continues on the next account. Tool errors are results the model reads (`error: …`), never a crashed run.
- Household members (`people`, id 1 = owner): bots, tasks, messages and asks carry `member`; a run uses the task member's own engine agent (`m<id>`), whose credentials are that member's alone; rests are keyed `<member>:<account>`. Never fall back onto another member's account (vendor terms). App connections (`src/connections.ts`) are per member too. A connected app is either remote MCP servers or crewd's own one-tool AXI on the member's token (`App.tool`; Calendar is `src/calendar.ts`, Gmail read-only `src/mail.ts`), whose commands `effectOf` gates like the browser's.
- API responses to the app carry no commands, paths, model or engine ids, percentages or prompts (`Crew.pub`/`task`/`askView`; asserted in `test/stub.test.ts`). The web app reads crewd only through `web/src/adapter.ts`; the contract is `docs/ui-contract.md`.
- Anything time-based is a row in `routines`, fired by `Crew.schedule()` from crewd's own tick (schedule words in `src/routines.ts`); no cron, no timers per routine. Chief offers a routine with `crew_routine`, and so can a helper for its own recurring check (a `watch` costs the person nothing on a quiet day; when only the bot's browser can read the page it is a `quiet` routine instead). Tests move `next_at` into the past and call `crew.schedule()` instead of waiting.
- Restart is a non-event: in-memory state in `Crew` (holds, live runs, handoffs) must be rebuildable from SQLite plus the session keys (`tasks.session`). `Crew.recover()` requeues running tasks, and `run()` continues the same session key; a parked question stays open and the resumed bot's retried call finds it. `test/restart.test.ts` kills a real crewd mid-run.
- A bot's core is plain files: `soul.md` (who it is; the person writes it, never a bot) and `AGENTS.md` (its job) in `bots/<id>/`, loaded in that order (`systemPrompt`). What the crew knows about a member lives in that member's folder, `people/<member>/` under the crew dir: `about.md` (every helper reads it) and `notes/<bot>.md` (one helper's), each capped and injected per task for the task's member only (`Crew.memory`). The member written to is the running task's, never a tool argument. Every change is a git commit in that folder (`src/bots.ts` `remember`/`forget`); Undo edits lines back rather than `git revert`, which conflicts on adjacent notes. `upgradeFolder` moves older layouts on start. A bot's **soul and job** change only through a card the person says yes to (`kind: 'propose'` asks: `crew_learn` keeps a skill, Chief's `crew_suggest` changes a soul; `Crew.adopt` applies it). Its **learned skills** change automatically — the engine's own workshop reviews a long finished turn and applies one skill into the member's workspace (`skills.workshop.autonomous.mode: auto`; crewd surfaces one `Learned: …` line and rows with Forget under `GET/POST /api/learned`, and Settings' "Learn from how I work" switches the mode through `Crew.setLearning`).
- A person's message in Chief's thread goes through `src/route.ts` first (`@byokit/decide`, pinned exactly): rules first; a miss becomes a Chief task. A plain helper request becomes that helper's task (origin `chief`); anything else starts a Chief task immediately, with no separate model turn.
- Chief's voice lives in `templates/chief/soul.md`, his job in `templates/chief/AGENTS.md`. First run is the app's Hello screen (greeting by the member's name, three ideas); tapping one calls `onboard(address, member, ask)`. The written `chiefGreeting` in `src/crew.ts` only greets a thread nobody has opened from Hello. A task with no usable account waits (`paused`, `wake_at` NULL) and `Crew.wake()` starts it once that member signs in.
- Latency is measured before it is changed: `node scripts/measure-firstwords.mjs --state <dir> --crew <dir> --runs 10` times the retained route's first real model words (a tiny prompt against Chief's real first-turn prompt) off the engine's own stream and reports per-run values, medians and prompt sizes; it refuses to start while crewd owns that state, and `test/firstwords.test.ts` runs it on the scripted provider. Chief's first turn as installed carries ~2.6k tokens (10,267 chars of system from `templates/chief/{soul.md,AGENTS.md}` plus the static block in `systemPrompt`, against a tiny prompt's ~14); the route's own floor is what a first-word claim has to be measured against, never a host-side millisecond.
- Home's third frame and the phone's list below the chats are the standing "hand me a job" list, straight from `ideas[]` through `A.jobs()` (`docs/ui-contract.md`): money back first, a row waiting on an app says what it needs and links to the apps screen, and a tap fills Chief's composer rather than sending; `ideas[].needs` may name a kit tool or a connected app (two of the household's Google apps name one thing: `Google`), and the six-row cap counts only rows ready to run. A job meant to land on a schedule belongs to a helper, not Chief: `ideas[]` publishes helper rows only and `planRoutine` refuses Chief, so "every weekday morning" is always a helper's task. `plain()` also folds runs of whitespace, so a helper's list reaches the chat with one return per item, never a blank line. The web UI is plain React bundled by `scripts/build-web.mjs`, on design direction C "Pocket Pals" (night mode and ASCII moments from A). Screens read only the plain-words view models in `web/src/adapter.ts`, never crewd rows; what the UI needs from crewd is `docs/ui-contract.md`, and `test/ui.test.ts` fails if a command, path, model name, percentage, monospace text or machinery word (relay, link, Noise, ticket, grant, host, daemon, crewd, engine, token, port, stub; Tailscale only where it is set up) can reach a screen. `?demo` runs every screen on `web/src/demo.ts`. `tokens.ts`, `art.ts` (the mascots as hand-placed dot bitmaps; Chief is "the Gentleman": moods live in his brows, moustache and bowler; the app icon, favicon and notification glyph are drawn from it by `node scripts/icons.mjs`, outputs committed), `adapter.ts` and `api.ts` stay framework-free, so the future Expo app can reuse them. It bundles `@desklink/react-native`'s `*.web.*` build with `react-native` aliased to `web/src/rn-web.tsx`; tsc checks `web/src/desklink.d.ts` instead of the package's Metro sources, and `.npmrc` (`legacy-peer-deps`) keeps its Expo peers out.
- The office is Home's top frame, one flat 2D room on both sides (`web/src/office.tsx` and `mobile/src/office.tsx`, from `A.office`/`officeEvent`): who sits where at any crew size is `A.floorPlan` (desks for Chief and helpers on your jobs, the lounge for the rest, "+N more" past two rows each; needs-you always keeps a desk), and `?demo=crew1|crew5|crew12|crew30` exercise it. The sprites are square pixels from `art.spriteSvg` (the phone's `mobile/assets/pals` PNGs come from it via `node scripts/icons.mjs`), the room's colours are `tokens.ts` `room`. Nothing moves while quiet: `test/office.test.ts` counts rAF calls and running animations in a headless `?demo=calm`/`?demo=office` run and checks no bubble overlaps at every crew size, at 390 and 1440; the phone moves only when an event lands (no timers; `motion.useAwake`).
- The relay (`relay/`, its own `package.json`, lockfile and image; not part of crewd's size budget) runs `@byokit/relay`, pinned exactly in both `relay/package.json` and the root one (tests import it from the root). `relay/main.ts` replaces two private `Relay` methods (content-free `notify`, open signup) as migration debt, not supported extension points; BYOKit must publish options for both before these patches are removed; `test/relay.test.ts` is the gate for a bump. Self-host only: there is no hosted Crewhouse relay and no built-in address; a family sets theirs in Settings (`link.relay`) or `CREWHOUSE_RELAY`. The person never types that address on the phone: the computer shows one code, `short`-`code`@<relay host> (`adapter.phoneTyped`), and `readTyped` (mobile/src/typed.ts) splits it, so the phone's single box takes a direct envelope or a relay code by shape.
- Phone push is migration debt, relay or not: BYOKit must own registration, delivery and the durable quiet-hours outbox; content-free NEWS, member rules and quiet-hour preferences remain product policy. Currently the app registers its Expo token over the link (`POST /api/push`, kept as settings `phone.push.<id>`) and `Link.tell` posts the content-free `NEWS` to Expo; tests point `CREWHOUSE_PUSH_URL` / `link.pushUrl` at a local stub. The app's Android push credential is dropped in, never committed (README, "Phone notifications"). The phone's offline words come from evidence (`adapter.away()`, `knock()`), never one guess.
- Bot desktops live in `src/desktop.ts` (Xvfb + the bot's Chromium + one desklink engine per bot). A distro Chromium wrapper can add Wayland and scale flags; the bot's flags come last so they win. Never let a bot process see the owner's `WAYLAND_DISPLAY` or X cookie. The bot's Chromium speaks DevTools over a pipe, relayed by crewd at a secret loopback WebSocket path: the sandboxed shell shares the host's loopback (`--share-net`), so any listening port is reachable from every bot's shell; `test/desktop.test.ts` runs that attack. That pipe is one client at a time, so crewd reads it (`Desktops.pages`/`clearSite`, and `Teacher`) only while the wheel is held or the bot's browser tool is detached, and flattened sessions carry `sessionId` at the message's top level, never inside `params` (see `teach.ts`).
- A template may list `net`, the only hosts its helper reaches (`src/net.ts`): its sandbox then has no network but a Unix socket to crewd's allowlisting proxy (bridged to `127.0.0.1:3128`, set as every `*_proxy`), `web_fetch`/`web_search` check the list on every hop, any other tool that reaches out on its own is refused at the gate, and every refusal is a `net.refused` event. The list is read from the repo's template, never the bot's folder (the bot can write that). The support desk is fenced: issue text is attacker-written input aimed at an agent.

Prefer rewriting or pruning existing entries over appending new ones.
