# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Checks: `npm run check` (tsc, strict) and `./crewhouse test` (a throwaway HOME, then a check that the owner's `~/.pi` sign-ins, settings and extensions are byte-for-byte unchanged). Run both before committing; CI (`.github/workflows/ci.yml`) runs them plus the web build on Node 24 (OpenClaw 2026.9.33 needs 24.16+ or 26.1+), so tests must never need an account, the network or a model: crew-logic tests run on the scripted `StubRuntime` (`src/stub-runtime.ts`, `CREWHOUSE_ENGINE=stub`; the script is in the file header), and the pinned Gateway's own tests run on the scripted HTTP provider (`test/openclaw-stub.ts`).
- Tests wait on a condition with a bound, never a fixed sleep: CI's disks are slow. This holds for a sleep you judge safe (a short one, or one waiting out a lifetime) and for sleeps already on main — a CI flake you traced to a fixed sleep is yours to convert, not to explain away. Use `test/lab.ts` (`setup`, `until`, `settled`, `holding`, `release`); daemon tests take an OS-assigned port.
- Node runs `src/*.ts` directly with type stripping: no parameter properties, enums or namespaces (tsconfig sets `erasableSyntaxOnly`). Imports use `.ts` extensions.
- Size budget: `test/line-budget.test.ts` owns crewd's (`src/`) ceiling and exception history. Every change keeps src/ net <= 0 unless the owner authorizes an exception; the Herdr first-slice exception is paired with trim lane ch-src-trim-s3. Prefer deleting to adding.
- The engine is OpenClaw, driven through the BYOKit OpenClaw kit (`@byokit/openclaw`, pinned exactly on npm). The kit owns the supervised child (env built from nothing: loopback bind, token auth, channels/Control UI/Tailscale/mDNS off), transport, sign-in wizard, runs, bridge plugin, engine installation (`prepare()`) and install policy; `src/openclaw/runtime.ts` is the only file that imports it (uses the retained engine agent `m1` and maps Crewhouse's `bash` to the model-visible `shell` — the engine rewrites a tool called bash to its own exec — and holds the tool schemas, Crewhouse's engine config and trusted skill list); `src/engines.ts` alone picks the engine from config, and `test/engine-seam.test.ts` pins both the import guard and the AgentRuntime contract — `test/openclaw-bridge.test.ts` fails otherwise, and exercises the kit's isolated `prepare()` installer; the kit's `engineDir` is `Config.engineDir` (`CREWHOUSE_ENGINE_DIR`): a git checkout or `scripts/package.mjs`'s `.deb` keeps `runtime/openclaw`, any other install (the desktop app in `desktop/` too) `~/.local/share/crewhouse/engine`; the kit's published `engine/` pin is authoritative, with no committed mirror. A kit gap goes to the BYOKit repo, never a Crewhouse-side patch; `test/kit-fake.ts` runs the port on the kit's fake Gateway. Standing helpers use the kit's same-agent helper sessions, adopting earlier `agent:m1:crewhouse:<bot>` conversations on their first native hand-off; Chief keeps `agent:m1:crewhouse:chief:<task>` (stored in `tasks.session`). Persona is session context, never Chief's identity written over a helper. Account coverage follows OpenClaw's supported subscription routes (spec §12 of data/ch-openclaw-found/spec.md); the pin-bound matrix lands with the sign-in step. Bump OpenClaw deliberately: `test/openclaw*.test.ts` (isolation, loopback, fail-closed gate) plus the stub suite are the gate.
- Sign-in goes through the engine's own wizard (`runtime.signIn`); `src/accounts.ts` is the person-facing shim: who is signed in (`ready`, keyed by account), the sign-in card view, and the states the product words come from (`expired`, `excluded` for a plan without helpers, `rests` for cooldowns). `classify` (`@byokit/accounts`) maps an engine error to those states. The kit listens on ChatGPT's fixed port 1455 (`CREWHOUSE_CALLBACK_PORT` in tests) during a browser sign-in (the redirect lands there); the device code is the fallback. The wizard hands over steps only when pulled with `wizard.next` — `wizard.status` answers `{status, error}` and never carries a step — and the engine admits one setup session at a time, so the kit cancels its own session with `wizard.cancel` on every exit short of done (test/openclaw-wizard.test.ts pins this on the real engine). The fs tracer the isolation test uses is in-repo: `test/trace-fs.mjs`.
- The upgrade migration (`runtime.migrate` + `confirm`, `test/openclaw-migrate.test.ts`) is staged and witnessed: the engine installs before doctor runs, doctor only runs while no gateway owns the state dir (the engine enforces this), its exit code is a weak yes, and the person's old auth is removed without a plaintext archive only after `models.authStatus` reports the sign-in. Stage legacy `auth.json` inside `auth-profiles.json` so doctor canonicalizes `openai-codex` to `openai` before SQLite import; already-retired originals can be repaired the same way. A failed import leaves the original in place; the next boot retries. The app's account list (`AIS` in `web/src/adapter.ts`) must match `PROVIDERS` in `src/accounts.ts` — `test/ui.test.ts` pins the keys; screen sources (.tsx) must not contain the word `claude` literally (scan at test/ui.test.ts), so account names/colours live in the adapter and their marks in `web/src/logos.ts` (the phone's PNGs come from it via `node scripts/icons.mjs`; `mobile/src/marks.ts` holds the requires).
- Finished files a model specs and crewd writes: spreadsheets `src/workbooks.ts` (`crew_workbook`, exceljs pinned exactly in `package.json`; `test/workbooks.test.ts` is the gate) and documents `src/documents.ts` (`crew_document`, docx pinned, read back through its own jszip/xml-js; `test/documents.test.ts`). The helper hands over a plain spec, the model never hand-writes the binary, and the app renders only crewd's JSON (`GET /api/workbook`, `GET /api/document`, delivery checked) — never the file. One card + one read-only panel serve both (web/src/parts.tsx `PreviewCard`/`PreviewPanel`).
- Policy is `src/policy.ts` `effectOf`, called from the engine's `tool_call` hook (`Crew.gate`): unknown tools fail closed. Work in the bot's space and the bubblewrap shell never asks; spending never gets a standing answer (its effect has no `key`). A press on a site the person signed the bot in to is a `send` with no `key` either, so it asks every time and its card names the button and the money read from the page's own snapshot (`policy.pressOf`, `Crew.press`) — never the model's description of what it is about to do. A claim form's lines are the person's own words: where the person signed the bot in, each line asks on its own card as `label: value`; a form the helper typed lines into asks its submit on any host, signed in or not, and that card lists every line. Card words come from the tool and its input, never the model. A job whose call acted out in the world (`policy.acts`) ends `done` only after `crew_outcome {worked: true}`; otherwise `unsure`, with a line and an alert like a failure. Only a call that itself came back ok marks the job: `Crew.gate` holds the mark while the call runs, so a click the engine refused before it ran changed nothing and raises no alarm. Likewise a delivered `*.patch` counts only after crewd's own `crew_verify` saw its check fail on the base and pass with it (both runs in the bot's sandbox; the exit codes are crewd's; each worktree is seeded with a copy of the bot's installed `node_modules`, and a before side that failed on a missing module is marked `missingDep` and never counts). A draft in the person's name goes on a `crew_draft` card that records approve or reject; nothing is sent either way. The one sending path is Tracer's email, through the guarded Gmail send in `src/mail-send.ts` (paired control phone, one card per message). `scripts/validate-support.mjs <task>` checks a support run against crewd's own `run.call` record and events, never the helper's word. Command-line tools needing the person's sign-in are typed host tools (`run.free`/`run.spend` in `tools/<id>/tool.json`), never shell.
- Tool kit: manifests in `tools/*/tool.json`, logic in `src/tools.ts` (`resolveGrants`, `installTool`). Tests set `CREWHOUSE_TOOLS_DIR` to a temp dir; a real `./crewhouse tools install` downloads Chromium (~170 MB). A pinned tool never resolves from the owner's PATH; with a `package-lock.json` beside its manifest it installs by `npm ci`, scripts off. Agent-facing tools prefer AXIs (https://axi.md) over MCP: one `args` schema per tool, not a server's dozens every turn. An AXI runs by absolute path on crewd's node with `axiEnv` (the bot's own HOME and every XDG dir: `XDG_CACHE_HOME` beats HOME), never `process.env`; `test/isolation.test.ts` checks the owner's whole HOME stays byte for byte.
- Which account a task runs on is picked in `src/crew.ts` `run()`: the bot's `models` in `bot.json` (keys of `PROVIDERS` in `src/accounts.ts`), each on the person's one model for that account (`account:model`, picked in Settings › AI accounts from the engine's `models.list`; `Crew.pickModel` puts it first in every bot.json, so Chief's holds every pick), skipping signed-out and plan-less ones (`usable`). Chief never picks a model or account for a task. A resting first account pauses the task until the rest ends or the person picks: never a switch to another AI by surprise. A signed-out or plan-less turn still fails over: the account is flagged, the task requeues with a handoff line, and the same session key continues on the next account. Tool errors are results the model reads (`error: …`), never a crashed run.
- One person per install (`people`, id 1). `Store.single()` refuses a shared database before the link loads grants; it must update through the P1 migration release (`bc37c20`) first, which preserves former people’s files and sign-ins on disk. Member columns and the old phone snapshot fields stay compatible. Crew reads only the person; `member` columns are inert except `reads` and `usage` writing id 1 for their primary keys. Runs use the retained engine agent `m1`; account state and rests are keyed by account alone. Legacy sign-in migration and weekly learned-skill curation address only this agent. App connections (`src/connections.ts`) use pinned `@byokit/connect` handles and the README's name-bound sealed-store adapter in `stateDir/people/1/app-signins/`; old sign-ins and setup keys are ignored, with no import path. A Google app's client comes from the kit's `googleClientFile` first (`~/.config/byokit/google-oauth-client.json`, `$CREWHOUSE_GOOGLE_CLIENT` via `Config.googleClient`), so it connects in one tap with no new OAuth client; the Settings paste (`setHouseGoogle`, `PUT /api/house/google`) is the fallback for a machine without the file, and only then are `house.steps` the four Cloud-console steps (with the file they are `null`). A Google connect ask is always Chief's (`askConnect` routes an `a.google` app to `CHIEF`), and `answer` resumes the helper's own task (`task.bot`). A connected app is either remote MCP servers or crewd's own one-tool AXI on the person's token (`App.tool`; Calendar is `src/calendar.ts`, Gmail is `src/mail.ts` — reads plus reply-as-draft and label filing through the guarded `MailSend` path on the separate `gmailwrite` grant, one card per message with no standing answer, never a send), whose commands `effectOf` gates like the browser's. Gmail sending (`src/mail-send.ts`, its own `gmailsend` connection) is not an app tool: no agent can call it.
- The web app reads crewd only through `web/src/adapter.ts`; `docs/ui-contract.md` owns the plain-words API contract and its exact terminal-approval exception (`Crew.pub`/`task`/`askView`; `test/stub.test.ts`, `test/run-tools.test.ts`).
- Anything time-based is a row in `routines`, fired by `Crew.schedule()` from crewd's own tick (schedule words in `src/routines.ts`); no cron, no timers per routine. Chief offers a routine with `crew_routine`, and so can a helper for its own recurring check (a `watch` costs the person nothing on a quiet day; when only the bot's browser can read the page it is a `quiet` routine instead). Tests move `next_at` into the past and call `crew.schedule()` instead of waiting.
- Restart is a non-event: in-memory state in `Crew` (holds, live runs, handoffs) must be rebuildable from SQLite plus the session keys (`tasks.session`). `Crew.recover()` requeues legacy running tasks, and `run()` continues the same session key; a parked question stays open and the resumed bot's retried call finds it. Interrupted native hand-offs are marked `unsure`, not silently replayed; their continuation is a follow-on slice. `test/restart.test.ts` kills a real crewd mid-run.
- A bot's core is plain files: `soul.md` (who it is; the person writes it, never a bot) and `AGENTS.md` (its job) in `bots/<id>/`, loaded in that order (`systemPrompt`). What the crew knows about the person lives in `people/1/` under the crew dir: `about.md` (every helper reads it) and `notes/<bot>.md` (one helper's), each capped and injected per task (`Crew.memory`). Memory always reads and writes `people/1/`; former people's folders stay untouched. Every change is a git commit in that folder (`src/bots.ts` `remember`/`forget`); Undo edits lines back rather than `git revert`, which conflicts on adjacent notes. `upgradeFolder` moves older layouts on start. A bot's **soul and job** change only through a card the person says yes to (`kind: 'propose'` asks: `crew_learn` keeps a skill, Chief's `crew_suggest` changes a soul; `Crew.adopt` applies it). Its **learned skills** change automatically — the engine's own workshop reviews a long finished turn and applies one skill into that run's own lane workspace — the member agent's, or the OpenCode Go key agent's (`skills.workshop.autonomous.mode: auto`; crewd logs automatic learning and curation without chat notices, and supplies rows with Forget under `GET/POST /api/learned`, and Settings' "Learn from how I work" switches the mode through `Crew.setLearning`).
- On OpenClaw, a person's message in Chief's thread starts a Chief task directly; Chief hands work to an available standing helper through native `sessions_send`. While a helper has the job, the gate holds Chief's run (no tool call of his own), so the report arrives in his next turn and he answers the person from it; the wait opens at the hand-off and closes when that turn ends.
- Chief's voice lives in `templates/chief/soul.md`, his job in `templates/chief/AGENTS.md`. First run has no Hello screen: after GettingReady the app opens Chief's chat, where `chiefGreeting` (src/crew.ts) asks the name; a short first message there is sent as `onboard(address, undefined, undefined, true)` (the name saved, Chief's `chiefPitch` added, no model), and the pitch shows `A.firstIdeas` as tap-to-send chips plus a local "How does this work?" (`FirstTry`, mobile's matching `Land` + chips). A task with no usable account waits (`paused`, `wake_at` NULL) and `Crew.wake()` starts it once the person signs in.
- Latency is measured before it is changed: `node scripts/measure-firstwords.mjs --state <dir> --crew <dir> --runs 10` times the retained route's first real model words (a tiny prompt against Chief's real first-turn prompt) off the engine's own stream and reports per-run values, medians and prompt sizes; it refuses to start while crewd owns that state, and `test/firstwords.test.ts` runs it on the scripted provider. Chief's first turn as installed carries ~2.6k tokens (10,078 chars of system from `templates/chief/{soul.md,AGENTS.md}` plus the static block in `systemPrompt`, against a tiny prompt's ~14); the route's own floor is what a first-word claim has to be measured against, never a host-side millisecond.
- Home (under the chat list, web and phone) carries the standing "hand me a job" list, straight from `ideas[]` through `A.jobs()` (`docs/ui-contract.md`): money back first, a row waiting on an app says what it needs and links to the apps screen, and a tap fills Chief's composer rather than sending; `ideas[].needs` may name a kit tool or a connected app (two of the person's Google apps name one thing: `Google`), and the six-row cap counts only rows ready to run. A job meant to land on a schedule belongs to a helper, not a named Chief: `ideas[]` publishes helper rows only and `planRoutine` refuses a routine that names Chief, so "every weekday morning" is always a helper's task — but a routine with no helper named is the person's own reminder and runs as Chief's task. `plain()` also folds runs of whitespace, so a helper's list reaches the chat with one return per item, never a blank line. The web UI is plain React bundled by `scripts/build-web.mjs`, on design direction C "Stack" (Archivo display type, bundled in `web/fonts` and `mobile/assets/fonts`, night mode). Screens read only the plain-words view models in `web/src/adapter.ts`, never crewd rows; what the UI needs from crewd, including screen-word restrictions and the terminal-approval exception, is owned by `docs/ui-contract.md` (`test/ui.test.ts`). `?demo` runs every screen on `web/src/demo.ts`. `tokens.ts`, `art.ts` (the faces are Geo: flat shapes with one trait each, on their own black disc, the same by day and night, with a card colour each (`colourOf`): Chief is the blue circle in a captain's cap, each template keys its own look by template id, and a helper Chief makes up gets one from `MADE` hashed by bot id (`A.kindOf`), never Chief's; the app's moods map onto four face modes, `faceOf` (via the five poses, `poseOf`), and web faces opt into Little nudge SVG motion (thinking lean, streamed-reply nods, one-shot done/ask; reduced motion stays still), without JS frame ticks or changing the default static PNG/icon output; the phone's `mobile/assets/pals` PNGs and `mobile/src/faces.ts` come from it by `node scripts/icons.mjs`, outputs committed; the app icon and favicon draw Chief's face; the notification glyph and phone bubble still draw the old helmet), `adapter.ts` and `api.ts` stay framework-free, so the future Expo app can reuse them. It bundles `@desklink/react-native`'s `*.web.*` build with `react-native` aliased to `web/src/rn-web.tsx`; tsc checks `web/src/desklink.d.ts` instead of the package's Metro sources, and `.npmrc` (`legacy-peer-deps`) keeps its Expo peers out.
- The web app's Home, chat and desktop shell are the calm design (`.shell.calm`, the last section of `web/src/styles.css`; the native `mobile/App.tsx` Home still shows a card per helper): one accent, warm amber, only on the person's own messages and what waits on them. Home on a phone is a chat list (`ChatRows`: Chief first, carrying "Chief has N things for you" and N while anything waits (`counts.needs`, a helper gone quiet included), then each helper by `A.chats` group order with its last line or "<name> is working", then The crew), the goal row, Hand me a job, and a floating dock (places menu + search). A computer at `#/` opens three panes: the same list on the left, Chief's thread in the centre, and the details column (Made in this chat, Also today) only when it has content. Threads float a translucent pill head (back, face and name, menu) over soft bubbles; a finished sheet or page is a compact attachment (`Attachment` in `web/src/parts.tsx`), never a full-width card. Crew rows never ask the person and carry no count. Every row and line clamps by class (`.clamp1`), so `scripts/verify/home-gate.mjs` can treat any other overflow as clipped. A resting account heads Home with what waits. `scripts/verify/home-states.sh <out> first|busy|resting` seeds each on the stub engine and runs the headless gate. Your crew (`#/crew`) shows the same members as tiles, Chief's saying his `A.chiefStatus` word, then The crew room. The office's one state is `useOffice` (`web/src/office.tsx`, `mobile/src/office.tsx`, from `A.office`/`officeEvent`): the list, tray and badge all count from it, and `?demo=crew1|crew5|crew12|crew30` exercise it (`?demo=thread` is the calm thread's reference). Face motion stays inside isolated SVG images. `test/office.test.ts` checks in a headless `?demo` run that no page animation loops or per-frame image rewrites run, and that no row overlaps or clips, body text is 16px or more and counts agree, at every crew size, at 390 and 1440.
- The relay (`relay/`, its own `package.json`, lockfile and image; not part of crewd's size budget) runs `@byokit/relay`, pinned exactly in both `relay/package.json` and the root one (tests import it from the root). `relay/main.ts` uses the kit's `contentFreeNotify` and capped `signup` options; `test/relay.test.ts` is the gate for a bump. Self-host only: there is no hosted Crewhouse relay and no built-in address; the person sets theirs in Settings (`link.relay`) or `CREWHOUSE_RELAY`; a cloud machine's install-time `CREWHOUSE_RELAY_PUBLIC` is the origin phones and typed codes use instead (`link.relayPublic`, docs/ui-contract.md). The person never types that address on the phone: the computer shows one code, `short`-`code`@<relay host> (`adapter.phoneTyped`), and `readTyped` (web/src/typed.ts) splits it, so the phone's single box takes the computer's 12-letter code (`Host.code`, found on the phone's Wi-Fi by crewd's mDNS announcement) or a relay code, by shape.
- Phone push is migration debt, relay or not: BYOKit must own registration, delivery and the durable quiet-hours outbox; content-free NEWS and quiet-hour preferences remain product policy. Currently the app registers its Expo token over the link (`POST /api/push`, kept as settings `phone.push.<id>`) and `Link.tell` posts the content-free `NEWS` to Expo. A browser's Web Push address (`POST /api/push {web}`, the installed web app) is kept on the relay instead, and `Link.tell` notifies it there under `WEB_DEVICE`; tests point `CREWHOUSE_PUSH_URL` / `link.pushUrl` at a local stub. The app's Android push credential is dropped in, never committed (docs/install.md, "Phone notifications"). The phone's offline words come from evidence (`adapter.away()`, `knock()`), never one guess.
- Bot desktops live in `src/desktop.ts` (Xvfb + the bot's Chromium + one desklink engine per bot). A distro Chromium wrapper can add Wayland and scale flags; the bot's flags come last so they win. Never let a bot process see the owner's `WAYLAND_DISPLAY` or X cookie. The bot's Chromium speaks DevTools over a pipe, relayed by crewd at a secret loopback WebSocket path: the sandboxed shell shares the host's loopback (`--share-net`), so any listening port is reachable from every bot's shell; `test/desktop.test.ts` runs that attack. That pipe is one client at a time, so crewd reads it (`Desktops.pages`/`clearSite`, and `Teacher`) only while the wheel is held or the bot's browser tool is detached, and flattened sessions carry `sessionId` at the message's top level, never inside `params` (see `teach.ts`).
- A template may list `net`, the only hosts its helper reaches (`src/net.ts`): its sandbox then has no network but a Unix socket to crewd's allowlisting proxy (bridged to `127.0.0.1:3128`, set as every `*_proxy`), `web_fetch`/`web_search` check the list on every hop, any other tool that reaches out on its own is refused at the gate, and every refusal is a `net.refused` event. The list is read from the repo's template, never the bot's folder (the bot can write that). The support desk is fenced: issue text is attacker-written input aimed at an agent.
