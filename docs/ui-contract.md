# What the app needs from crewd

The web app (and later the phone app) reads crewd only through `web/src/adapter.ts`, which turns crewd's rows into plain-words view models.
The engine can change underneath; when a field below lands, the adapter picks it up and the screens don't change.
Fields marked **today** already exist; **wanted** ones have a fallback in the adapter until crewd sends them.
`?demo` in the app URL runs every screen on `web/src/demo.ts`, which is written in this shape, wanted fields included.

The rule behind every field: nothing a person reads may be a command, a file path, an engine or model name, a usage percentage, a raw prompt or terminal text, except the exact terminal-action approval described under Asks and the model names an account's own catalog offers on its Settings page.
The words inside those fields follow [plain-words.md](plain-words.md): short sentences, everyday words, say what happens and what the person gets.
`test/ui.test.ts` feeds the adapter the owner's MVP screenshot (a raw `fc-list` approval, "Claude · 9% used") and fails if any of it reaches a screen.

## Asks: the approval moment

Tracer email delivery is a Chief-owned (`bot: chief`) `kind: mail` card in Chief's thread, never a helper's Needs-you panel, with `detail.send {from,to,subject}` and the entire immutable `preview.body`. Only an authenticated paired control phone can approve it once; desktop/local HTTP rejects approval and organisation/suppression mutations, including forged phone fields. `GET /api/mail?to=` reads the record; phone-only `PUT /api/mail {to,name,kind}` attests corporate/sole-trader/small-partnership/unknown status (person, phone, server time and organisation domain), `{to,suppressed}` changes the do-not-email list (it works on free-mail addresses too; attestation of a free-mail domain is refused), and `POST /api/mail/review {draft}` prepares one card. Eligibility is not message approval. Unknown, sole-trader, small-partnership and suppressed recipients are refused; the checks run again before the single-use send claim. The separate `gmailsend` connection never exposes an agent sending tool. The desk disables Copy and Approve on Tracer email drafts; the phone still shows them, de-emphasised and not disabled. The only send path is `POST /api/mail/review` from the paired phone's **Review one email**. Only a Gmail 4xx (it answered and sent nothing) reopens the draft for a new review; any other failure, 5xx included, is an uncertain card ("Did this email go out?"). Successful/uncertain attempts are never automatically retried; an uncertain card's acknowledgement (`answer: 'dismiss'`, "OK, got it") may be sent from either device; no batch or standing sending approval exists.

Gmail drafting/filing permissions also carry `detail.mail {action, id}` (`draft` or `label`); the id binds the approval and is never screen copy. A parked approval and reused open card bind the task, message, action and full preview. The adapter says **Create draft** / **Apply label** and **Nothing will be sent**, never Send; the draft preview preserves formatted text. An answered card says Allowed, not Sent. The actual draft uses the person's send-as/signature and excludes every own send-as from recipients; a thread without a correspondent refuses. The Apps row for `gmailwrite` says **On · changes ask first**, not read only.

Today a permission ask carries `title` and `detail.{effect, words, spends, covers, always}`, written by crewd's gate from the tool and its input, never by the model:
`effect` is `send`, `spend`, `delete` or `files`; `words` is the sentence ("Reel wants to change a file in your Documents folder: “plan.txt”."); `always` is what "Always OK" would cover, and is absent for spending.
There is no `summary`, `tool` or `rule`. Herdr drives are the explicit exception to command scrubbing: `effect: 'send'` with `preview: {head: 'The exact command', body, verbatim: true}`. The body is the complete JSON argument array, with non-ASCII characters escaped; `words` includes that same array as the approval identity. The adapter preserves both without trimming or scrubbing and uses neutral **Needs your OK** / **Yes, go ahead** wording, not email wording. Every drive asks separately, with no standing answer; looking uses a `files` ask whose standing answer covers terminal-agent reads. `test/run-tools.test.ts` pins identity and presentation; `test/draft-copy.test.ts` checks sheet fit.
Every "Not now" also offers "Remind me tomorrow" (`POST /api/asks/:id/answer {answer:'deny', remind:true}`): the deferred question is filed as a one-shot routine that raises it with the helper again tomorrow at 9, then is gone.
A checkout page (a `spend` from the browser) carries `preview` `{head, body}`: the order's lines as the page writes them and its total, read by crewd from the browser tool's own page snapshot, never the model's words, with the shop's host only. Its total is the spend's cost toward the monthly cap when it is in dollars; a price in another currency says so on the card and never counts, and when the total can't be read, the words say so and it doesn't count. One yes covers that page's later clicks until the page or the total changes. A checkout ask also carries `order` `{shown, known, dollars}` for the review sheet: `shown` is the total as the page writes it, `known` whether crewd could read one, `dollars` whether it counts toward the cap — never the page's address. Cards for a checkout are review-first: the inbox opens the review and offers "Don't place order"; the sheet's yes names the order ("Place order · $43.10"); with no readable total there is no yes — "Don't place order" and "I'll buy it myself".
Pressing something on a site the person signed the bot in to (a `send` from the browser — a shop's claim button, a returns form) carries the same `preview`: the button's own name and the page's few lines around it, read by crewd from the browser tool's own page snapshot, and its `words` name the button, the host, and any money the page shows. A form the helper fills (a claim's lines) is the same card family: where the person signed the bot in, each line asks on its own card, shown as `label: value` — the label as the page writes it, the value from the tool call; and the press that submits a form the helper typed lines into asks on any host, signed in or not, its card carrying every line (`fill: true`, so the app's yes reads "Yes, fill it in" — "Yes, fill these in" for more than one line — never "press"). The "a site you signed it in to" clause is said only when the helper really has a sign-in for that site. Such sends have no `key`, so `always` is absent: there is no standing answer for acting as the person on their sites, and every ask is its own card (the owner's decision of 2026-09-26). Such a `send` carries `press: true` (the app titles the card "…wants to act on a site" and its yes "Yes, press it", never "…message is ready to send" / "Send"), and has no `key`, so `always` is absent: there is no standing answer for acting as the person on their sites, and every press is its own card (the owner's decision of 2026-09-26).

## The crew room

`#/room` is a view of existing task messages, not a second chat. `GET /api/room?before=` returns qualifying job lines `{id,bot,author,to?,from?,text,at,standup?}`, open asks and busy bot ids. Qualifying means a room-started job, or a Chief job he handed on natively to two or more helpers (one hand-off is an errand and stays in his thread). A hand-off is a line `from: chief, to: <helper>` whose text is Chief's own brief to that helper (the `sessions_send` message, never the person's request); a helper's answer is its own line. Helpers do not hand work to each other: only Chief delegates. `state.room` provides the pinned Chats row's last line and busy ids. The person can talk directly to any helper: `POST /api/bots/:id/messages {text,room}` addresses the selected helper, and `room:true` rejoins that helper's latest room job. Chief remains the default chat. The room is read-only. The standup is Chief's closing words on a job that ended `done` (his last bot message on the root task), flagged `standup: true` and headed "Chief's standup"; only when his job ends failed or unsure, or has no words of his own, does crewd stand in with one deterministic wrap-up (`room.wrap`, the same flag). A delivered file in the room is a file card.

## Messages: `GET /api/bots/:id` (today)

`POST /api/bots/:id/messages {text, photos?, files?}`: `photos` is up to four `{type: 'image/jpeg' | 'image/png' | 'image/webp', data: base64}` (5 MB each; the phone and the web app send about 1280 px JPEG so it fits one link frame). They are kept in the helper's `files/photos/` (so they show in Things), given to the model with the words, and ride in the chat line as `[photo <bot>] files/photos/…`, which `adapter.lines()` turns into pictures. `files` is up to four documents alongside them, each `{name?, type, data: base64}` (`application/pdf`, docx, xlsx, `text/csv`, `text/plain`, `text/markdown`; 10 MB each). They are kept in the helper's `files/inbox/` under crewd's own `<task>-<n>.<ext>` name (the client's `name` is display-only and never becomes a path), named in the task for the documents tool to read, and ride in the chat line as `[file <bot>] files/inbox/… <bytes>B <name>`, which `adapter.lines()` turns into a file chip (name, kind, size). Anything else is refused in plain words. `GET /api/photo?bot&path` returns one such photo as `{type, data}` for the phone, which can't open this computer's `/files` address.

`POST /api/bots/chief/messages {text, move}`: a chat with Chief on the phone alone (no computer), carried over once the phone is paired (mobile `ContinueOffer`). `text` is the whole chat as one message, one Markdown list item per turn after one opening line (the thread folds blank lines and joins single ones, so nothing follows the list), who said what in order (a turn cut off on the phone marked stopped, a queued one not sent yet, so Chief answers it), a phone document as its title only (the file stays on the phone), the oldest turns left out past 40,000 characters with a note. It becomes one Chief task with no routing or inline answers, and `move` (1-64 word characters or hyphens, the chat's last request id) is its idempotency key: a resend returns the first result and stores nothing. The phone retires its copy (into a hidden archive sign-out erases) only after this answers; a failure or a 30-second silence (the link's `notValidAfter`, so a late computer never starts it) keeps the copy.

Chief's stop square (web and native, shown while his live line is open and the box is empty) calls `POST /api/bots/chief/reset`. The stopped job's line ("I stopped “…”, as you asked.") carries its task id, as a failure line does. In Chief's thread, `adapter.lines()` sets `retry` on the last line of a job that ended stopped or failed, to the person's own ask for that job, and the chat shows **Try again**, which re-posts that ask as a new job.

`POST /api/bots/:id/steer {text}` adds the person's words to the helper's running job: it reads them after its current step, without starting over. steering a helper that isn't working on anything is a 409.

A delivered workbook (`*.xlsx`, made by `crew_workbook`) rides in the chat as `Delivered files/<name>.xlsx: N sheets: …`, shown as a workbook card: its name, how many sheets, a peek at the first sheet's headings, **Open**. `GET /api/workbook?bot&path` reads it back as words only — `{sheets: [{name, total, rows[], nums[], roles[][], charts[]}]}`, heading row first, at most 500 rows × 24 columns per sheet (all a `crew_workbook` sheet can hold), formulas as their cached value or one crewd works out from the cells (blank when it can't), never the formula text, row numbers with gaps where blank rows were skipped, per-cell roles (`head`, `in`, `calc`, or empty, from formulas and dropdowns only) — parsed crewd-side with crewd's own exceljs; `charts` are the bar, line and pie charts on that sheet (`crew_workbook`'s optional `charts`, which crewd writes as real chart parts pointing at the sheet's cells) as `{type, title, labels[], series: [{name, values[]}]}`, the numbers read from those cells, at most 8 a sheet. The app renders it read-only (sheet tabs, each chart drawn over the table, a table, **Download**), never the file. Only a delivered file may be read (403 otherwise). `#/f/<helper>/<file>` opens the panel beside the chat that delivered it: side panel on a desk, whole screen on a phone.

A delivered `*.patch`/`*.diff` is a **review**: crewd's own check on it (`crew_verify`) is the verdict, in its words only. The delivery line reads `Delivered files/x.patch: Suggested change (for the maintainer to review)` and nothing more — the verdict is one line per check run, said by the check itself in plain words with no path in it (a path on a screen is mangled, and the person reads what happened to their change, not where it is kept): `The suggested change passed its own check.`, or `The suggested change did not pass its own check — <what the check found>` (the same check still fails after the change; it passed before the change and fails after it; it could not run: something it needs is not installed; it passes here but never failed before, so nothing was proved), with `An earlier check said otherwise; this run is the current one.` when a newer run overturns an older. A job whose only unfinished business is that change says so in the helper's own words and adds no verdict of its own. Beside the file, `adapter.reviews()` builds the card from crewd's own `verify.result` events in `state.events`: the verdict, the finding, when it ran, and **Start it again** (`POST /api/bots/:id/task/:task/again`) when it did not pass — the same task in the same session with the verdict in its handoff, never a second job. A newer run on the same change is the current one, and a card whose verdict changed says so. In the crew room as in a helper's chat, crewd's own lines are notes and only a helper's or the person's words are a bubble.

The same shape of story for documents: a delivered `*.docx` (made by `crew_document`) is a card too, and `GET /api/document?bot&path` returns `{parts: [{kind: 'heading'|'p'|'li'|'table', text, bold?, head?, rows?}]}` — plain words crewd parsed out of the file (docx + its own jszip/xml-js), at most 150 parts, scrubbed like chat words; no markup, no paths, no formulas. A delivered `*.pptx` (made by `crew_slides`, one title and its lines per slide) reads through the same endpoint as `{slides: [{title, lines[]}], parts}`: the slides the panel draws one frame each, and the same words flattened as parts, so a reader without frames shows a deck too. A delivered `*.md` or `*.txt` reads through the same endpoint as `{text}` — the file's own words, capped — which the panel (and the phone's sheet) render with the shared safe markdown renderer (`web/src/chat-md.ts`): headings, tables, read-only ticks, http(s)-only links, scrubbed line by line like chat words. A written page never opens as the raw `/files/` address; every place a delivered file opens by URL (`A.fileTarget`) sends pages and sheets to `#/f/…` instead, and keeps PDF/xlsx/docx/pptx on their existing viewers. The rule any file the web can show the phone can show: the phone's reader opens the same parsed words (`GET /api/document` for a document or page, `GET /api/workbook` for a spreadsheet) and never says "on your computer" for one; `crew_document` never leaves a shorter companion copy behind, either — one finished document. A delivered video rides the same rule in pieces: `GET /api/video?bot&path&after` → `{data, more, size}`, base64 slices a link frame's worth, delivery checked; the phone fetches it to its cache and plays it in its own player (portrait media shows whole, `contentFit: contain`).

`messages[]` `{author: person|bot|chief|system, text, helper?}`; in Chief's thread `helper` records the source of the finished job or question, but Chief is the only speaker shown to the person; both apps render it as Chief. A confirmed action's final reply keeps its complete receipt facts (unknown facts stay absent), rather than the ordinary 160-character relay opening. A helper captures its actual result with its existing browser screenshot command into `files/photos/…`, then delivers it; delivered pictures show inline, uncropped, and tap open full size (on the phone over `/api/photo`, at most 900 KB). No synthetic result pictures. A file already carried inline in Chief is not repeated as a tray notice; a system text `Delivered files/x.mp4: note` becomes a media card. Chief's hand-off in a helper's thread also carries its task's `title`; `adapter.lines()` collapses it to one short ask — `Chief asked: <title>`, the full assignment words behind **Show details** (`line.detail`) on the phone — so the result leads; the web's read-along shows the ask alone under "Chief to <name>", and folds a file delivered on its own line into the helper's next words. A teaser (`things[].summary`, the chat list's line) reads as plain words with no raw `**` emphasis (`adapter.teaser`).
A job ends `done`, `failed` or `unsure`: it acted out in the world (sent, bought, deleted, pressed or typed on a page) and the helper didn't say it saw it work. crewd then writes a bot line starting "Not sure it worked:" in the helper's chat (a routine's goes to Chief's thread as "Pip isn't sure “…” worked. …"), raises the same `alert` a failure does, and the trail gets `task.unsure`; `adapter.lines()` marks such a line `unsure` and the chat sets it apart.
Chief's daily recap is a separate message with `recap: true`, supplied by the routine's recorded message id. Both apps keep its author and time visible even after another Chief message; the web sets it apart as a card. It appears at most once per local day, including after a restart. Quiet days get one calm line; other recaps include only useful updates.

Without words: **Deal with this** and **Is this real?** (in a chat or mail app) take a still, **Scan a letter** a camera photo, and each opens the share screen with that helper picked and the words in its box, one tap from someone else. **Is this real?** asks for warning signs, never a verdict, and never to open what it points at; on words, its web addresses are defanged first (`hxxp://`, `[.]`), since the ask's words are the only fence (a still can't be). **Put this date in my calendar** needs Google Calendar and **Find that email** Gmail: until they are connected the label says so and a tap opens Settings; the calendar add itself is the usual ask card.
**Remember this** sends no job: the phone checks the words first (`adapter.keep()`: digits that look like a PIN, a card number or a one-time code, and web or email addresses, are refused before anything is sent), then adds one `- …` line to what the whole crew knows (`GET`/`PUT /api/about`), with Undo taking that line back out.
Chief's box answers two things itself, with no model: who is on what (`crewLine()` and what needs the person) and what the crew knows about them (their name and `GET /api/about`), each with **Ask Chief anyway**. "Plan my day" is Scout's own day-plan ask, a job like a button's.
**Write it here** shows while a box had focus: the writer (Scribe, else the general Helper) drafts for the box as an ordinary job (`adapter.writeAsk()`; its reply is the draft, `adapter.draftOf()`), and **Put it in** fills that same box through the kit; nothing is sent, the person presses the app's own Send. On Reddit or in a Hacker News reader (`adapter.notesOn()`, by the box's app) the ask is for labelled notes the person writes their own reply from, and **Copy** puts them on the clipboard in place of **Put it in**. The X and LinkedIn apps keep prose and **Put it in**, with no still: `@byokit/overlay` 0.3.0's screen-frame needs a foreground Crewhouse screen, so it can't take one of the app while its box keeps focus.

## Phones

`GET /api/phones` → `[{id, name, role, seen, online, reached, push}]` (`reached`: when the phone last reached this computer over each route, `{home?, tailscale?, relay?}`, worded by `adapter.reached()`; `push`: `on`, `off` (the person said no on the phone), `missing`, or absent); `POST /api/phones/pair {role: 'control'|'view'}` → `{qr, typed, expires, urls}` (`typed`: @byokit/pair's 12-letter `Host.code`, as single use and short-lived as the QR, with the same two words and yes; the phone finds the computer by its mDNS announcement below, the web app at its own address; on the computer or its enrolled headless-owner phone; every paired phone uses the person's crew, with watch-only phones unable to answer or give jobs). A headless host's opt-in first-owner code includes its private relay address as `short-code@relay` instead, without a computer-side confirmation; see [Install](../install.md#headless-linux-host).
`DELETE /api/phones/:id`; `GET /api/phones/link`, `PUT /api/phones/lan {on}` and `PUT /api/phones/relay {url, enrol?}` → `{on, lan, pinned, tailscale, anywhere, hosts, web, relay, relayPublic, relayStatus, push, asking: [{id, name, words, role, offer?}]}`. `push` is `missing` when a phone's app build has no Android push credential or Expo refused it, else `ready`; `adapter.pushWords()` says it once. `vapid` is the relay's Web Push key the browser subscribes with (`null` without a relay).
`POST /api/push {web}` subscribes this browser's `PushSubscription` JSON at the relay (409 with no relay or no `web` object); `{off: true, web}` removes it (400 without a `web` object). A paired device sends the same body over the link, where its `web` address is kept and removed under its own grant id — so the installed PWA turns notifications on and off away from the computer too — and may ask `{key: true}` for the relay's public Web Push key first (`{ok, vapid, online}`; `vapid` is `null` without a relay, which the app says in plain words, never a broken toggle). Both return `{ok}`. Ordinary paired apps cannot read `/api/phones/link` over the link, and Settings' notifications switch reads the key over `/api/push` instead.
`anywhere` is `home` (no Tailscale: phones reach this computer only on the home Wi-Fi), `anywhere` (a Tailscale address is bound) or `signin` (Tailscale is installed but signed out, or its key ran out); `adapter.anywhere()` gives the sentence and the numbered steps still to do. Phones dial the Tailscale address directly (`ws://`), never through Serve or Funnel, and the phone signs in to the same Tailscale account as the computer, or the person shares this computer with that phone's account in Tailscale. Offline instructions address the person directly and keep the different-account case.
`lan` is the person's "home network" setting. On an unpinned desktop host, with it off, `hosts` still includes `0.0.0.0` for the two minutes a pairing code is showing, so a phone can pair over the home Wi-Fi; while the home network is open crewd also announces itself over mDNS (`_crewhouse._tcp`, TXT `{id, url}`), so a paired phone finds it again after the router hands it a new address.
`relay` is the person’s own relay address crewd dials (`''`, the default: none; there is no hosted Crewhouse relay). `url` is an `https://` or `wss://` address (`http`/`ws` for a local relay), `''` for none, or `null` to go back to `CREWHOUSE_RELAY`. A cloud install sets `CREWHOUSE_RELAY_PUBLIC` at boot to the provider's public origin instead of crewd's loopback dial address; `relayPublic` is that value, else `relay`, and no relay save changes it. Invalid input returns 400 without changing the connection. Offers, `link.urls`, `/api/reach` and typed codes advertise this public origin; local dial, enrolment and relay notifications still use `relay`.
`web` is the https address of the computer's own web app (`''` until set). `PUT /api/phones/web {on: true}` shares it through Tailscale (`serve` on the link port + 1; 409 with plain words when signed out) and `{address}` takes the person's own server's (`{on: false}` clears); with it set, the pairing `qr` is `<web>/#byokit-link:…`, a link the phone's camera opens, and the web app pairs from that address.

`relayStatus` is `off`, `connecting`, `online`, `offline`, `refused` (the relay didn't let this computer in: paste a new invitation) or `replaced`; `adapter.reach()` words it. `PUT /api/phones/relay` also takes `enrol`, a one-use invitation from a relay that lets computers in by invitation; it is dropped once used.
`POST /api/phones/code {role}` → `{short, code, relay, expires}`: codes to type on the phone instead of scanning, once `relayStatus` is `online` (409 before). The phone types one code, `adapter.phoneTyped()`'s `short`-`code`@<relay host>, the go-between's address carried inside it; `readTyped` (web/src/typed.ts) tells a relay code from the 12-letter code by its shape, so the one box takes either and the person never types an address.
A bot's screen on the phone: a link stream `desktop` with `{bot}` carries the same messages as the computer's `/ws/desktop/:bot` socket, one JSON per line (`{id, method, params}` in; `{id, result | error}` or `{event}` out). A watch-only phone may open it but never gets the controls. Take control and Hand it back are the usual `POST /api/bots/:id/takeover` and `/giveback`. On give back, `GET /api/bots/:id/screen` → `{pages: string[]}` names the bare hosts on its tabs (the one on screen first), read by crewd off its own DevTools pipe while the wheel is held, so the sheet can tick "I signed {Name} in to <host>" — the visible tab's host ticked, the rest clear; `/giveback` takes `keep: string[]`, which must be among those hosts (a host with no tab is a 400), and only a tick adds the host to `signedIn`.
Over the link only, for the phone itself: `GET /api/reach {via, ip}` → `{urls, anywhere, peer, reached}` (every address it can reach this computer at now: home network, Tailscale, the relay; the phone adds each to its grant, and gets the same list live as a `link.urls` event whenever it changes. `via` is the route it came by (`home`, `tailscale` or `relay`) and `ip` its own Tailscale address; `peer` says whether this computer's Tailscale has that address as a peer. The phone keeps `anywhere`, `peer` and `reached` for when it can't reach the computer, and `adapter.away()` turns them, with what it sees for itself and a bounded `adapter.knock()` on the computer's address, into what was observed and what to try) and `POST /api/push {expo} | {missing} | {off} | {web} | {key}` (its Expo push token, kept by crewd, which sends through Expo; `missing`: this app build has no push credential; `off` without a browser address: the person said no; a browser's `web` address is kept on the relay under the calling device's own grant id, and `{off: true, web}` removes it there so off really means no pushes; `{key: true}` answers the relay's public Web Push key and whether it is online, for a paired browser's own switch). The raw Expo registration/delivery and durable outbox are migration debt awaiting BYOKit notification contracts; notification words and quiet-hour preferences stay in Crewhouse. Every push says only "Crewhouse has news": a question for that person, their job finished, failed or not sure it worked, or Chief speaking to them. In their quiet hours the push is held (kept in the store) and one is sent when they end, however much came in.
A phone that scans an ordinary code waits in `asking` until the person compares its two words and answers `POST /api/phones/answer {id, yes}`. A headless host's first-owner code is the exception below.
The one phone-admin call a paired phone makes itself: `POST /api/phones/refresh {message}`, the person's phone renewing the Add-a-phone code it is looking at, so the pairing card on the phone refreshes itself like the web card's — while the card is on screen it asks for a fresh code when the countdown ends, stops after about ten minutes idle, and a **Show a new code** button takes over. A `member` field is refused with 426 and “Update the Crewhouse app”. A card whose phone already joined never refreshes (409); every other `/api/phones` call from an ordinary phone still answers `403 do that on the computer`.
Computer-only account, settings and phone administration also accept the enrolled headless-owner phone's encrypted control grant (`src/link.ts`, on `@byokit/pair`). A 404, or `on: false`, shows "The phone app is on its way".
The phone app (`mobile/`) reads crewd through this same adapter and `web/src/api.ts`, with the link as its transport: each call is one request `METHOD /path`.

**Headless first owner:** authenticated loopback `POST /api/phones/pair {role:'control',first:true}` is enabled only by the headless runner, with no prior owner or phones. The existing two-minute BYOKit offer returns `{qr,typed,expires,urls}` and auto-confirms only that locally minted ticket; concurrent handshakes admit one owner. Its device id is recorded durably and grants the same account/settings/phone-administration authority as the host's `person.key`, without exposing that key. No phone can mint a first-owner offer. Used, expired, superseded and previous-process first codes fail closed; revocation does not reopen bootstrap. The headless runner pins loopback and its Tailscale IP (never opens LAN), and its private relay enrols only this host. Ordinary pairing and watch-only restrictions do not change.

## Unreachable

Any request that fails without an HTTP status is "the home computer isn't answering": a full screen before first load, a banner after.
Both retry by themselves and say "Back in touch" when it answers again.

## Chief's profile

`#/h/chief/details`, opened from Chief's hero (his face or name) and the desk's "Chief's profile" link: Routines (the first two of `A.routines`, a switch each, "+ Add routine" opening the same `RoutineAsk`), Computer (a live, watch-only look at the crew member on a computer and one **Take control**, which is `POST /api/bots/:id/takeover` and lands on that helper's Screen with **Hand it back**), Notifications and Instructions. `GET /api/notify` → `{on}` and `PUT /api/notify {on}` are "Tell me when Chief finishes or needs me": on by default; off, `Link.tell` sends no content-free news to any phone or browser. Instructions (`#/h/chief/instructions`) shows Chief's personality, which the person changes there or in Settings (**Change**, **Put back how Chief started**), and the read-only plain-words limits of his job (`GET /api/bots/chief` `rules`: the job's Boundaries lines that name no tool), which change only through a card the person says yes to (`Crew.adopt`). Things (`#/h/chief/files`, `/links`, `/pictures`, one switch between them) lists what is in Chief's chat, newest first and read-only, from the same `GET /api/bots/chief` lines and `state.tasks` the thread draws (`A.chatThings`): Files (uploads and deliveries, including the helpers' finished files the thread notes), Links (http(s) links said in it), Pictures (photos and videos); each has its own empty state, and the profile row and the list both say "Pictures". On crew rows (Chats) a dot means working, nothing else; unread and asks belong to the thread they appear in.

The hand-off you can see: in Chief's thread each job Chief handed a helper (`task.origin: 'chief'`) is one chip, `Asked <helper>` with the helper's face, linking to the helper's chat, after the turn that handed it on and before its result (`A.handChips`); its status is the app's one word (`A.WORDS`), said for screen readers and shown beside a tick once done, with a dot only while working; the job itself is the live card below it (the helper's colour, its title, its status, the check list and **Open**). On that helper's first hand-off only, above it one sentence says what the helper can do and that it can't pay or send anything without asking (`A.limitOf`), built only from crewd's grants — `bots[].can` (granted, ready tool ids), `bots[].signedIn` (hosts) and `connections` — never the model's words; paying and sending always ask (`effectOf`), so that half is always true. A helper's chat has its own composer and sends to that helper. Its idea chips and a hire's first job still fill Chief's composer as `<helper>, …`. The side menu's crew row is the helper's face, name and one status word (`A.roster`).

## Learning and the work trail

`GET /api/learned` → `[{id, skill, at, state}]` — the skills the engine learned from your work on any model lane (the member agent and the OpenCode Go key agent), one row per skill name, the newest copy winning: pending ones and the applied ones still loaded; `POST /api/learned/forget {id, skill}` forgets it on every lane that holds it (a pending one is rejected; an applied one is captured, then put away in that lane's `skills/.archive`, never deleted). The bot page's settings show these as **Learned · Forget** rows under the **Learn from how I work** switch.
`GET /api/learning` → `{on}` and `POST /api/learning {on}` are that switch: the engine's own learning mode, on by default. The switch applies to your crew.
`GET /api/task/:id/trail` → `[{at, words, ok}]` — one plain-words row per tool call of one task, recorded by crewd itself (`run.call`), redacted to words. A call whose result reads `error: …` is a failure: `ok` is false and its words say the call could not do it. The "How I did it" drawer renders it collapsed by default.

**The receipt** for a message the person answered is the same trail, not a second place to look: `draft.approved` / `draft.rejected` are in a bot's `trail` (`TRAIL`, `src/crew.ts`), and `adapter.receipt(kind, data)` renders one plain line — what was answered (the subject, or the first words of a text or post), where it went (the real recipient), that **nothing was sent, you send it yourself**, and, when the draft carried one, `because you said “<why>”`. Its words are the ones actually put on the card, the person's own if they edited them. An approved receipt whose `why` is one of that helper's own notes also offers **Forget that**, which removes that line through `PUT /api/bots/:id/notes` (`adapter.withoutMemory`), so the next job reads notes afresh; that is the only memory write in this surface.

`GET /api/events?after=` returns up to 200 newer events in sequence order. The web socket and paired phones receive every live event; helper trails retain their own event kinds without a viewer filter. New durable events have no member tag; `alert` notifies the person’s phones. `bot.models` carries only `{by: 'person'}` and `system.engine` carries `{}`; each database open also scrubs the historical payloads of both kinds.

An install serves one person (id 1); screens need no role selector. Creating or listing people at `/api/people`, requesting Google setup at `/api/house/ask`, and `…/ask-owner` are no longer supported. The person's editable settings keep `PUT /api/people/1`. Snapshots emit `person.id: 1` and `house: {google, steps}`; `members` and `member` on live `reply.partial` are gone. Phone builds older than P9b are unsupported: each encrypted request and desktop stream carries `build: "p9b"`. Unmarked phones get an empty Home snapshot whose Chief chat row says “Get the latest Crewhouse app to keep chatting.”, with no `members` or real asks. `GET /api/bots/chief` returns only that sentence with a link to the current preview, so the old phone can open it. Other requests answer 426 with the notice, and desktop streams end with it. The computer’s HTTP API needs no phone marker. Every request under `/api/`, GET included, requires the private `person.key` capability in `Authorization: Bearer …`, as well as `x-crewhouse: 1` for CSRF protection; every `/ws` upgrade requires it in `crewhouse-person.…` as its protocol. A delivered file's raw `GET /files/<bot>/<path>` accepts only the `crewhouse-files` cookie, since a helper's shell shares the loopback. The cookie is an HMAC of the key (never the key), set by `POST /api/files/session` (bearer + `x-crewhouse`, HttpOnly, SameSite=Strict, `Path=/files`), which the web app sends at boot and again when the home computer comes back (`api.mintFiles`); a link, `<img>` or `<video>` then loads the plain `/files/` address with Range support. The launcher passes it through a fragment, removed immediately into tab-local sessionStorage. Pairing administration uses the same boundary; authenticated control-phone requests keep their existing rights, and view-only grants still cannot write. Shared installs must update through P1 (`bc37c20`) before this build will start.
