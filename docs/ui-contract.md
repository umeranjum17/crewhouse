# What the app needs from crewd

The web app (and later the phone app) reads crewd only through `web/src/adapter.ts`, which turns crewd's rows into plain-words view models.
The engine can change underneath; when a field below lands, the adapter picks it up and the screens don't change.
Fields marked **today** already exist; **wanted** ones have a fallback in the adapter until crewd sends them.
`?demo` in the app URL runs every screen on `web/src/demo.ts`, which is written in this shape, wanted fields included.

The rule behind every field: nothing a person reads may be a command, a file path, an engine or model name, a usage percentage, a raw prompt or terminal text, except the exact terminal-action approval described under Asks.
`test/ui.test.ts` feeds the adapter the owner's MVP screenshot (a raw `fc-list` approval, "Claude · 9% used") and fails if any of it reaches a screen.

## Asks: the approval moment

Tracer email delivery is a Chief-owned (`bot: chief`) `kind: mail` card in Chief's thread, never a helper's Needs-you panel, with `detail.send {from,to,subject}` and the entire immutable `preview.body`. Only an authenticated paired control phone can approve it once; desktop/local HTTP rejects approval and organisation/suppression mutations, including forged phone fields. `GET /api/mail?to=` reads the record; phone-only `PUT /api/mail {to,name,kind}` attests corporate/sole-trader/small-partnership/unknown status (person, phone, server time and organisation domain), `{to,suppressed}` changes the do-not-email list, and `POST /api/mail/review {draft}` prepares one card. Eligibility is not message approval. Unknown, sole-trader, small-partnership and suppressed recipients are refused; the checks run again before the single-use send claim. The separate `gmailsend` connection never exposes an agent sending tool. The desk and phone disable Copy and Approve on Tracer email drafts; the only send path is `POST /api/mail/review` from the paired phone's **Review one email**. Successful/uncertain attempts are never automatically retried; no batch or standing sending approval exists.

Today a permission ask carries `title` and `detail.{effect, words, spends, covers, always}`, written by crewd's gate from the tool and its input, never by the model:
`effect` is `send`, `spend`, `delete` or `files`; `words` is the sentence ("Reel wants to change a file in your Documents folder: “plan.txt”."); `always` is what "Always OK" would cover, and is absent for spending.
There is no `summary`, `tool` or `rule`. Herdr drives are the explicit exception to command scrubbing: `effect: 'send'` with `preview: {head: 'Exact terminal arguments', body, verbatim: true}`. The body is the complete JSON argument array, with non-ASCII characters escaped; `words` includes that same array as the approval identity. The adapter preserves both without trimming or scrubbing and uses neutral **Needs your OK** / **Yes, go ahead** wording, not email wording. Every drive asks separately, with no standing answer; looking uses a `files` ask whose standing answer covers terminal-agent reads. `test/run-tools.test.ts` pins identity and presentation; `test/draft-copy.test.ts` checks sheet fit.
Every "Not now" also offers "Remind me tomorrow" (`POST /api/asks/:id/answer {answer:'deny', remind:true}`): the deferred question is filed as a one-shot routine that raises it with the helper again tomorrow at 9, then is gone.
A checkout page (a `spend` from the browser) carries `preview` `{head, body}`: the order's lines as the page writes them and its total, read by crewd from the browser tool's own page snapshot, never the model's words, with the shop's host only. Its total is the spend's cost toward the monthly cap when it is in dollars; a price in another currency says so on the card and never counts, and when the total can't be read, the words say so and it doesn't count. One yes covers that page's later clicks until the page or the total changes. A checkout ask also carries `order` `{shown, known, dollars}` for the review sheet: `shown` is the total as the page writes it, `known` whether crewd could read one, `dollars` whether it counts toward the cap — never the page's address. Cards for a checkout are review-first: the inbox opens the review and offers "Don't place order"; the sheet's yes names the order ("Place order · $43.10"); with no readable total there is no yes — "Don't place order" and "I'll buy it myself".
Pressing something on a site the person signed the bot in to (a `send` from the browser — a shop's claim button, a returns form) carries the same `preview`: the button's own name and the page's few lines around it, read by crewd from the browser tool's own page snapshot, and its `words` name the button, the host, and any money the page shows. A form the helper fills (a claim's lines) is the same card family: where the person signed the bot in, each line asks on its own card, shown as `label: value` — the label as the page writes it, the value from the tool call; and the press that submits a form the helper typed lines into asks on any host, signed in or not, its card carrying every line (`fill: true`, so the app's yes reads "Yes, fill it in" — "Yes, fill these in" for more than one line — never "press"). The "a site you signed it in to" clause is said only when the helper really has a sign-in for that site. Such sends have no `key`, so `always` is absent: there is no standing answer for acting as the person on their sites, and every ask is its own card (the owner's decision of 2026-09-26). Such a `send` carries `press: true` (the app titles the card "…wants to act on a site" and its yes "Yes, press it", never "…message is ready to send" / "Send"), and has no `key`, so `always` is absent: there is no standing answer for acting as the person on their sites, and every press is its own card (the owner's decision of 2026-09-26).

| `preview` `{head, body}` | `{head: "To Aunty Sara · from your Gmail", body: "Dear Aunty Sara, …"}` | Exactly what goes out, in the sheet |
| `chief` | "A lovely note, if I may say so." | Chief's line under the preview |

A connection a task needs is an ask with `kind: 'connect'` and `detail.{app, words}` ("Let Pip use your Google Calendar"), opened by the helper's `crew_connect` tool.
It shows as a card in that helper's chat, never on Home. Answer `allow` once connected (the app does it by itself), `deny` for Not now; the task carries on either way.

## The crew room

`#/room` is a view of existing task messages, not a second chat. `GET /api/room?before=` returns qualifying job lines `{id,bot,author,to?,from?,text,at,files:[{bot,path}]}`, open asks and busy bot ids. Qualifying means a room-started job or a helper-to-helper handoff (including one waiting on a check). `state.room` provides the pinned Chats row's last line and busy ids. `POST /api/bots/:id/messages {text,room:true}` starts in the room and rejoins that helper's latest room job; Chief still routes normally. The per-helper `handoff` setting is `go` (default) or `ask`; `ask` opens a proposal with Hand it on / Not now, never Always. A multi-part job gets one deterministic Chief wrap-up linked to its root task when all parts and handoff cards settle. The room shows the person's qualifying tasks and cards.

## Messages: `GET /api/bots/:id` (today)

`POST /api/bots/:id/messages {text, photos?}`: `photos` is up to four `{type: 'image/jpeg' | 'image/png' | 'image/webp', data: base64}` (5 MB each; the phone sends about 1280 px JPEG so it fits one link frame). They are kept in the helper's `files/photos/` (so they show in Things), given to the model with the words, and ride in the chat line as `[photo <bot>] files/photos/…`, which `adapter.lines()` turns into pictures. `GET /api/photo?bot&path` returns one such photo as `{type, data}` for the phone, which can't open this computer's `/files` address.

`POST /api/bots/:id/steer {text}` adds the person's words to the helper's running job: it reads them after its current step, without starting over. steering a helper that isn't working on anything is a 409.

A delivered workbook (`*.xlsx`, made by `crew_workbook`) rides in the chat as `Delivered files/<name>.xlsx: N sheets: …`, shown as a workbook card: its name, how many sheets, a peek at the first sheet's headings, **Open**. `GET /api/workbook?bot&path` reads it back as words only — `{sheets: [{name, total, rows[], nums[], roles[][]}]}`, heading row first, at most 500 rows × 24 columns per sheet (all a `crew_workbook` sheet can hold), formulas as their cached value or one crewd works out from the cells (blank when it can't), never the formula text, row numbers with gaps where blank rows were skipped, per-cell roles (`head`, `in`, `calc`, or empty, from formulas and dropdowns only) — parsed crewd-side with crewd's own exceljs; the app renders it read-only (sheet tabs, a table, **Download**), never the file. Only a delivered file may be read (403 otherwise). `#/f/<helper>/<file>` opens the panel beside the chat that delivered it: side panel on a desk, whole screen on a phone.

A delivered `*.patch`/`*.diff` is a **review**: crewd's own check on it (`crew_verify`) is the verdict, in its words only. The delivery line reads `Delivered files/x.patch: Suggested change (for the maintainer to review)` and nothing more — the verdict is one line per check run, said by the check itself in plain words with no path in it (a path on a screen is mangled, and the person reads what happened to their change, not where it is kept): `The suggested change passed its own check.`, or `The suggested change did not pass its own check — <what the check found>` (the same check still fails after the change; it passed before the change and fails after it; it could not run: something it needs is not installed; it passes here but never failed before, so nothing was proved), with `An earlier check said otherwise; this run is the current one.` when a newer run overturns an older. A job whose only unfinished business is that change says so in the helper's own words and adds no verdict of its own. Beside the file, `adapter.reviews()` builds the card from crewd's own `verify.result` events in `state.events`: the verdict, the finding, when it ran, and **Start it again** (`POST /api/bots/:id/task/:task/again`) when it did not pass — the same task in the same session with the verdict in its handoff, never a second job. A newer run on the same change is the current one, and a card whose verdict changed says so. In the crew room as in a helper's chat, crewd's own lines are notes and only a helper's or the person's words are a bubble.

The same shape of story for documents: a delivered `*.docx` (made by `crew_document`) is a card too, and `GET /api/document?bot&path` returns `{parts: [{kind: 'heading'|'p'|'li'|'table', text, bold?, head?, rows?}]}` — plain words crewd parsed out of the file (docx + its own jszip/xml-js), at most 150 parts, scrubbed like chat words; no markup, no paths, no formulas. The panel renders them read-only with **Download**, same delivery check. A delivered `*.md` or `*.txt` reads through the same endpoint as `{text}` — the file's own words, capped — which the panel (and the phone's sheet) render with the shared safe markdown renderer (`web/src/chat-md.ts`): headings, tables, read-only ticks, http(s)-only links, scrubbed line by line like chat words. A written page never opens as the raw `/files/` address; every place a delivered file opens by URL (`A.fileTarget`) sends pages and sheets to `#/f/…` instead, and keeps PDF/xlsx/docx on their existing viewers. The rule any file the web can show the phone can show: the phone's reader opens the same parsed words (`GET /api/document` for a document or page, `GET /api/workbook` for a spreadsheet) and never says "on your computer" for one; `crew_document` never leaves a shorter companion copy behind, either — one finished document. A delivered video rides the same rule in pieces: `GET /api/video?bot&path&after` → `{data, more, size}`, base64 slices a link frame's worth, delivery checked; the phone fetches it to its cache and plays it in its own player (portrait media shows whole, `contentFit: contain`).

`messages[]` `{author: person|bot|chief|system, text, helper?}`; in Chief's thread `helper` names the helper whose finished job or question a bot line carries, in its own words, so the line shows that helper's face and name; a system text `Delivered files/x.mp4: note` becomes a media card. Chief's hand-off in a helper's thread also carries its task's `title`; `adapter.lines()` collapses it to one short ask — `Chief asked: <title>`, the full assignment words behind **Show details** (`line.detail`) — so the result leads. A teaser (`things[].summary`, the chat list's line) reads as plain words with no raw `**` emphasis (`adapter.teaser`).
A job ends `done`, `failed` or `unsure`: it acted out in the world (sent, bought, deleted, pressed or typed on a page) and the helper didn't say it saw it work. crewd then writes a bot line starting "Not sure it worked:" in the helper's chat (a routine's goes to Chief's thread as "Pip isn't sure “…” worked. …"), raises the same `alert` a failure does, and the trail gets `task.unsure`; `adapter.lines()` marks such a line `unsure` and the chat sets it apart.
Chief's daily recap is a separate message with `recap: true`, supplied by the routine's recorded message id. Both apps keep its author and time visible even after another Chief message; the web sets it apart as a card. It appears at most once per local day, including after a restart. Quiet days get one calm line; other recaps include only useful updates.

**Wanted**: `choices: string[]` on a bot message, shown as tap-to-reply chips ("Soft & sweet", "Upbeat").
`trail` (events) becomes the "What I did" step list; `run.tool` events carry crewd's own plain `words` ("Searched the web for “school trips”", "Worked on a video", "Used its browser").
While a job is open, every thread ends in one live line (`adapter.liveLine`): who is on it, a clock counting up from crewd's own event times, and the job as a to-do list — plan-level rows done and doing (the model's own `task.progress` notes, deliveries and asks, each naming its object, never repeated), an approved plan's steps still to do, and the small `run.tool` calls kept behind the expand — and in the thread where the person asked, the helper's list mirrored with a link to its chat. It is built only from what `/ws` pushes and the thread's `trail`: `task.created` (with `origin`), `task.working`, `run.tool`, `file.delivered`, `ask.opened`/`ask.answered`, `task.paused`, a `reply.partial` (the whole reply so far, never cut) and the end (`task.done`/`failed`/`unsure`), which folds it into "Done · 14 s · 3 steps". Nothing on it is guessed: until crewd answers, it says only "Reading your message".
**Wanted**: a crewd-written `task.progress` for each meaningful step ("Picked 8 photos from Eid"), because that is what makes the list worth reading.

## Who a helper is, and what the crew knows about you (today)

`GET /api/bots/:id` also carries `soul` (who the helper is, in plain sentences under a `# Name` heading), `soulCap`, `skills[]` `{name, says}` (`says` is the skill in the person's words; the app never shows `description`), and `notes`: what that helper learned about **the person**, at `crewDir/people/1/notes/:id.md`. It also carries `signedIn`: the bare hosts of the sites the person signed this helper in to. Details shows the list ("Signed in to", host + **Forget** each, `adapter.signedIn()`); `POST /api/bots/:id/forget {host}` takes one back and clears it from the helper's browser.
`PUT /api/bots/:id/soul` `{text}` saves the person's words (the app keeps the `# Name` heading); `POST /api/bots/:id/soul/reset` puts back how it started. No bot can change its own.
`PUT /api/bots/:id/job` `{does, aim, gets, how, great}` changes a helper's five-part job; each part is capped at 600 characters and the total at 3,000. The job is only the `## Your job` section of its `AGENTS.md`. `POST /api/bots/:id/job/draft` `{idea}` asks Chief to change that helper's job; he answers on the adapt card below, and nothing changes until its yes.

`PUT /api/bots/:id/notes` `{text}` is the person's notes with that helper. `GET`/`PUT /api/about` `{notes, cap}` is what the whole crew knows about the person: every helper reads it before a job for them. A `memory.learned` step with `everyone` went there; Undo edits the person's lines and commits the correction; former people's memory events stay hidden.
`GET`/`PUT /api/profile` `{text, cap}` is About me and my work: Chief's merged sentences about the person and their work, which every helper reads before a job for them. Settings shows each sentence as its own part to change, forget or add to; the next job reads what the person saves.

A **suggestion** is an ask with `kind: 'propose'` and `detail.{words, preview: {head, body}}`: a skill a helper would like to keep (from `crew_learn`) or a new personality Chief suggests (from `crew_suggest`). A **hire** is Chief's `crew_create` card: its detail carries `hire` (the helper's name), `yes` ("Yes, take Pip on") and a `preview.body` of at most three lines (the role, what it can and can't do, its first job), never the five-part job; `allow` makes the helper and starts that first job, whose result comes back in Chief's thread. When Chief adapts a helper already on the crew instead, which is also how any asked-for change to a helper's job arrives, the detail also carries `adapt: true`, `yes` reads "Yes, Penny can take it on" and the first line says what the helper will do ("Penny now keeps your invoices and receipts in order."): `allow` rewrites that helper's job and role (who it is and its tools stay), says "From now on, Penny keeps …" in Chief's thread and starts the first job, if any, the same way. Suggestions are yes-or-no cards, never "always"; nothing changes until `allow`, and they wait across restarts. A **plan** is a propose ask from Chief whose detail carries `plan: {bot, steps}`: before a job of several steps starts, the card lists the steps with Go / Change it / Not now. `allow` hands the job to that helper; `{answer:'deny', change}` closes it and sends the person's words (shown in Chief's thread) back to Chief for a new plan. Go approves no send, spend or change: those still ask on their own cards. A helper's draft in the person's name (`crew_draft`) is a propose ask too: its detail also carries `draft` (with `channel` — `email`, `message` or `post`, what was really written, so the card's “wrote your …” is true; a post never carries a subject and crewd refuses one that does — the actual recipient `to`, and an email’s separate `subject`), its `preview.body` is one finished message with line breaks preserved, and its `yes` reads Copy. A draft may carry an `link` (`https` only, at most 500 characters; anything else is an error and files no card): then the `yes` reads Copy and open, copies the words the person sees (their edit when they made one) and opens that page before sending today's Approve answer. Both apps show the same short headline, recipient, subject and scrollable body with Copy / Edit / Reject; only social posts say “post it yourself”, emails and texts say “send it yourself”. `crew_draft` may carry `why`, the person's own line the draft answers; crewd keeps it only when it is one of the lines the crew remembers them saying (`about.md` or that helper's notes, matched whole), and drops the helper's own note about the draft, so the card's “Because you said “…”” under the recipient is always the person's words or absent. It is kept on the receipt below, where Forget takes that same line back. Helper draft decisions are carried in Chief's thread and Office panel by the adapter, not as a helper's Needs-you action; the original ask and file still belong to their writer. A marketing campaign reuses one post draft: Scribe delivers `files/campaign-<short-name>.txt`, with a channel heading then each exact post, separated by `\n\n---\n\n`, and calls `crew_draft` once without a link. Related tasks and their delivered PNG are found through their existing `root`. Its web review waits for those parts to settle and shows both posts and the poster with **Approve / Not now**. Neither answer copies, opens a page or sends anything. Approve records the existing draft decision and offers a separate **Copy post** per section plus **Save poster**. The web reads the full approved text through `GET /api/document` and checks the receipt's SHA before enabling copying; changed text asks for a fresh draft rather than copying an unreviewed version. Recent outcome cards use the existing 80-event snapshot window; the writer's trail keeps the durable receipt. Native Expo outcome controls are not added by this web slice.

The ordinary draft card's **Edit** lets the person change the words first: `POST /api/asks/:id/answer {answer:'allow', scope:'once', text}` keeps their version in the draft's file (the approval records its hash and `edited`); nothing is sent either way.

`skills[]` rows carry `learned`; `DELETE /api/bots/:id/skills/:name` puts a learned one away (kept, no longer used). A skill it came with can't be removed.

## First run (today)

`POST /api/onboard` `{address, ask, bot?}`: how Chief addresses the person and, from an idea card, their first request, in one tap. Only this explicit choice, Settings, or a request to change how they are addressed supplies the name; an ordinary first chat message starts a task with no name.
Her Chief thread then starts with that request. From the goal starter it also carries `bot: 'scout'`: crewd hires Scout when missing and the person's account runs helpers, and the request starts as her own Scout task instead. On a plan without helpers it starts with Chief. With no AI account yet it waits (a `paused` task with no wake time) and Chief says one line ("Before we start: the crew thinks with your own ChatGPT, the same one you already use."); the app shows the sign-in right under it. Signing in starts it by itself, and Chief says "You're signed in. Thank you, Sara. On it now."

## Sign in with ChatGPT (today)

`GET /api/accounts` rows `{account, name, signedIn, restingUntil, signIn, notIncluded, work}` for the person's accounts; the app reads `account: 'chatgpt'`. The `:member` segment on account actions stays for compatibility and is ignored.
`POST /api/accounts/:member/chatgpt/login` answers at once with `signIn: {state: 'waiting', via: 'browser', url}`: ChatGPT's own page, which the app opens in a tab it opened in the same tap (so it is never blocked as a pop-up). ChatGPT sends that tab back to crewd's own listener on port 1455, which shows Crewhouse's words only once the sign-in works; the sheet moves on when `signedIn` turns true.
`{via: 'code'}` ("Having trouble?") turns the same sign-in into `{via: 'code', code, url}`; crewd does it by itself when the page hasn't come back in three minutes. `{fresh: true}` asks ChatGPT's page which account again ("Use my personal account").
A sign-in that fails ends as `signIn: {state: 'failed', error, why?}`: `why: 'declined'` (Cancel on ChatGPT's page), `why: 'busy'` (something else on this computer is signing in to ChatGPT), or `error` saying "expired"/"took too long"; each has its own words in the app.
`work` is the email of a work ChatGPT (Business, Enterprise, Edu), read from the sign-in itself; the app offers "Use my personal account".
`notIncluded`: the plan has no helpers (ChatGPT's `usage_not_included`). `…/retry` is "I've changed my plan".
`…/cancel` stops a sign-in, `…/logout` signs out. Other supported accounts use the same actions with their account key in place of `chatgpt`; the offered list is in [supported-subscriptions.md](supported-subscriptions.md).

## Skills (today)

The Skills screen (`#/skills`, reached from Apps) lists the reviewed starter set and searches the public catalog.
Nothing installs by itself: only reviewed skills switch on, through the engine's own install with the trust check.

| Call | Returns |
|---|---|
| `GET /api/skills` | `{live, starter: [{slug, owner, version, summary, why, needs, on}]}` — the reviewed set; `on` as the engine sees it. `live: false` on the stand-in engine (all off) |
| `GET /api/skills/search?q=` | `{results: [{slug, owner, summary, version}]}` — the catalog's own matches, empty while the engine starts |
| `POST /api/skills/:slug/on` | Switches a reviewed skill on through the engine's install (the trust check still applies); 400 in plain words otherwise |
| `POST /api/skills/:slug/off` | Switches it off again |

The same skills answer to the OpenClaw way against this install (`openclaw skills search/install/list`), through the same engine and the same trust check — the app and the command line see the same set. Only the crew's own vetted plugins run; plugin installs stay in the official scope.

## Chief on your screen: the bubble (Android, today)

The phone app's own floating Chief (`mobile/src/bubble.ts`, the one file that imports `@byokit/overlay`), off until the person switches it on in Settings. It holds the phone's link and needs nothing new from crewd: every button is a call the app already makes.
A tap opens his panel (`mobile/src/panel.tsx`) over whatever app is in front; a long press opens it listening, the mic started by the panel, never the bubble's window, and what was heard waits in Chief's box until the person sends it.
The panel shows, top to bottom: Chief's line and `adapter.crewLine()` (who is on what, and when a resting account is back, from state alone, with no model turn); up to three of `needsYou()`, with **Take the wheel from {Name}** (`POST /api/bots/:id/takeover`, then that helper's screen in the app) and **Watch {Name}** (also on a watch-only phone) for the first of them whose helper has its own computer; at most three buttons from `adapter.quick()`; and Chief's box.
`quick()` is a rules table, never a model: the first three rows that fit what the tap read (the focused box's app, its words and the part picked; read once, on the tap, never a password box) are the buttons, and the overlay kit's tap log (app and button only, no words, 30 days) puts the one the person picks most in that app first; it never adds one. With no box in focus the kit names no app (`focusedField.read()` is null and `@byokit/overlay` 0.3.0 has no other foreground-app read in JS), so the panel shows the two that work on any screen, **Deal with this** and **Scan a letter**. Each button is fixed words to one helper, that template's when hired, else the general Helper (`POST /api/recruit {template: 'helper'}` when nobody is, and only once there is something to send; never Chief, whose hand-offs carry no photos), sent as an ordinary `POST /api/bots/:id/messages`. On words: **Put this date in my calendar** (a date), **Is this real?** (a web address or pressure words), **Find that email** (a booking, order or receipt; read-only Gmail), **Remember this** (a part picked), **Look it up** and **Short version** send them (the part picked, if any), and wait for the job's reply in the panel (its own `result`, as Write it here does). Without words: **Deal with this** and **Is this real?** (in a chat or mail app) take a still, **Scan a letter** a camera photo, and each opens the share screen with that helper picked and the words in its box, one tap from someone else. **Is this real?** asks for warning signs, never a verdict, and never to open what it points at; on words, its web addresses are defanged first (`hxxp://`, `[.]`), since the ask's words are the only fence (a still can't be). **Put this date in my calendar** needs Google Calendar and **Find that email** Gmail: until they are connected the label says so and a tap opens Settings; the calendar add itself is the usual ask card.
**Remember this** sends no job: the phone checks the words first (`adapter.keep()`: digits that look like a PIN, a card number or a one-time code, and web or email addresses, are refused before anything is sent), then adds one `- …` line to what the whole crew knows (`GET`/`PUT /api/about`), with Undo taking that line back out.
Chief's box answers two things itself, with no model: who is on what (`crewLine()` and what needs the person) and what the crew knows about them (their name and `GET /api/about`), each with **Ask Chief anyway**. "Plan my day" is Scout's own day-plan ask, a job like a button's.
**Write it here** shows while a box had focus: the writer (Scribe, else the general Helper) drafts for the box as an ordinary job (`adapter.writeAsk()`; its reply is the draft, `adapter.draftOf()`), and **Put it in** fills that same box through the kit; nothing is sent, the person presses the app's own Send. On Reddit or in a Hacker News reader (`adapter.notesOn()`, by the box's app) the ask is for labelled notes the person writes their own reply from, and **Copy** puts them on the clipboard in place of **Put it in**. The X and LinkedIn apps keep prose and **Put it in**, with no still: `@byokit/overlay` 0.3.0's screen-frame needs a foreground Crewhouse screen, so it can't take one of the app while its box keeps focus.

## Phones

`GET /api/phones` → `[{id, name, role, seen, online, reached, push}]` (`reached`: when the phone last reached this computer over each route, `{home?, tailscale?, relay?}`, worded by `adapter.reached()`; `push`: `on`, `off` (the person said no on the phone), `missing`, or absent); `POST /api/phones/pair {role: 'control'|'view'}` → `{qr, typed, expires, urls}` (on the computer only; every paired phone uses the person's crew, with watch-only phones unable to answer or give jobs);
`DELETE /api/phones/:id`; `GET /api/phones/link`, `PUT /api/phones/lan {on}` and `PUT /api/phones/relay {url}` → `{on, lan, pinned, tailscale, anywhere, hosts, relay, relayStatus, push, asking: [{id, name, words, role, offer?}]}`. `push` is `missing` when a phone's app build has no Android push credential or Expo refused it, else `ready`; `adapter.pushWords()` says it once.
`anywhere` is `home` (no Tailscale: phones reach this computer only on the home Wi-Fi), `anywhere` (a Tailscale address is bound) or `signin` (Tailscale is installed but signed out, or its key ran out); `adapter.anywhere()` gives the sentence and the numbered steps still to do. Phones dial the Tailscale address directly (`ws://`), never through Serve or Funnel, and the phone signs in to the same Tailscale account as the computer, or the person shares this computer with that phone's account in Tailscale. Offline instructions address the person directly and keep the different-account case.
`lan` is the person's "home network" setting. With it off, `hosts` still includes `0.0.0.0` for the two minutes a pairing code is showing, so a phone can pair over the home Wi-Fi; while the home network is open crewd also announces itself over mDNS (`_crewhouse._tcp`, TXT `{id, url}`), so a paired phone finds it again after the router hands it a new address.
`relay` is the person’s own relay, which phones use away from home (`''`, the default: none; there is no hosted Crewhouse relay). `url` is an `https://` or `wss://` address, `''` for none, or `null` to go back to `CREWHOUSE_RELAY`.
`relayStatus` is `off`, `connecting`, `online`, `offline`, `refused` (the relay didn't let this computer in: paste a new invitation) or `replaced`; `adapter.reach()` words it. `PUT /api/phones/relay` also takes `enrol`, a one-use invitation from a relay that lets computers in by invitation; it is dropped once used.
`POST /api/phones/code {role}` → `{short, code, relay, expires}`: codes to type on the phone instead of scanning, once `relayStatus` is `online` (409 before). The phone types one code, `adapter.phoneTyped()`'s `short`-`code`@<relay host>, the go-between's address carried inside it; `readTyped` (mobile/src/typed.ts) tells a relay code from the long direct envelope by its shape, so the one box takes any code and the person never types an address.
A bot's screen on the phone: a link stream `desktop` with `{bot}` carries the same messages as the computer's `/ws/desktop/:bot` socket, one JSON per line (`{id, method, params}` in; `{id, result | error}` or `{event}` out). A watch-only phone may open it but never gets the controls. Take over and give back are the usual `POST /api/bots/:id/takeover` and `/giveback`. On give back, `GET /api/bots/:id/screen` → `{pages: string[]}` names the bare hosts on its tabs (the one on screen first), read by crewd off its own DevTools pipe while the wheel is held, so the sheet can tick "I signed {Name} in to <host>" — the visible tab's host ticked, the rest clear; `/giveback` takes `keep: string[]`, which must be among those hosts (a host with no tab is a 400), and only a tick adds the host to `signedIn`.
Over the link only, for the phone itself: `GET /api/reach {via, ip}` → `{urls, anywhere, peer, reached}` (every address it can reach this computer at now: home network, Tailscale, the relay; the phone adds each to its grant, and gets the same list live as a `link.urls` event whenever it changes. `via` is the route it came by (`home`, `tailscale` or `relay`) and `ip` its own Tailscale address; `peer` says whether this computer's Tailscale has that address as a peer. The phone keeps `anywhere`, `peer` and `reached` for when it can't reach the computer, and `adapter.away()` turns them, with what it sees for itself and a bounded `adapter.knock()` on the computer's address, into what was observed and what to try) and `POST /api/push {expo} | {missing} | {off} | {web}` (its Expo push token, kept by crewd, which sends through Expo; `missing`: this app build has no push credential; `off`: the person said no; a browser's `web` address is kept on the relay). The raw Expo registration/delivery and durable outbox are migration debt awaiting BYOKit notification contracts; notification words and quiet-hour preferences stay in Crewhouse. Every push says only "Crewhouse has news": a question for that person, their job finished, failed or not sure it worked, or Chief speaking to them. In their quiet hours the push is held (kept in the store) and one is sent when they end, however much came in.
A phone that scans the code waits in `asking` until the person compares its two words and answers `POST /api/phones/answer {id, yes}`.
The one phone-admin call a paired phone makes itself: `POST /api/phones/refresh {message}`, the person's phone renewing the Add-a-phone code it is looking at, so the pairing card on the phone refreshes itself like the web card's — while the card is on screen it asks for a fresh code when the countdown ends, stops after about ten minutes idle, and a **Show a new code** button takes over. A `member` field is refused with 426 and “Update the Crewhouse app”. A card whose phone already joined never refreshes (409); every other `/api/phones` call still answers `403 do that on the computer`.
These answer on the computer only, never over the phone link (`src/link.ts`, on `@byokit/link`). A 404, or `on: false`, shows "The phone app is on its way".
The phone app (`mobile/`) reads crewd through this same adapter and `web/src/api.ts`, with the link as its transport: each call is one request `METHOD /path`.

## Unreachable

Any request that fails without an HTTP status is "the home computer isn't answering": a full screen before first load, a banner after.
Both retry by themselves and say "Back in touch" when it answers again.

## Learning and the work trail

`GET /api/learned` → `[{id, skill, at, state}]` — the skills the engine learned from your work (`state: 'applied'` is what the rows show); `POST /api/learned/forget {id, skill}` puts one back the way it was (the engine's own restore; nothing else runs). The bot page's settings show these as **Learned · Forget** rows under the **Learn from how I work** switch.
`GET /api/learning` → `{on}` and `POST /api/learning {on}` are that switch: the engine's own learning mode, on by default. The switch applies to your crew.
`GET /api/task/:id/trail` → `[{at, words, ok}]` — one plain-words row per tool call of one task, recorded by crewd itself (`run.call`), redacted to words. The "How I did it" drawer renders it collapsed by default.

**The receipt** for a message the person answered is the same trail, not a second place to look: `draft.approved` / `draft.rejected` are in a bot's `trail` (`TRAIL`, `src/crew.ts`), and `adapter.receipt(kind, data)` renders one plain line — what was answered (the subject, or the first words of a text or post), where it went (the real recipient), that **nothing was sent, you send it yourself**, and, when the draft carried one, `because you said “<why>”`. Its words are the ones actually put on the card, the person's own if they edited them. An approved receipt whose `why` is one of that helper's own notes also offers **Forget that**, which removes that line through `PUT /api/bots/:id/notes` (`adapter.withoutMemory`), so the next job reads notes afresh; that is the only memory write in this surface.

`GET /api/events?after=` returns up to 200 newer events in sequence order. The web socket and paired phones receive every live event; helper trails retain their own event kinds without a viewer filter. New durable events have no member tag; `alert` notifies the person’s phones. `bot.models` carries only `{by: 'person'}` and `system.engine` carries `{}`; each database open also scrubs the historical payloads of both kinds.

An install serves one person (id 1); screens need no role selector. Creating or listing people at `/api/people`, requesting Google setup at `/api/house/ask`, and `…/ask-owner` are no longer supported. The person's editable settings keep `PUT /api/people/1`. Snapshots emit `person.id: 1` and `house: {google, steps}`; `members` and `member` on live `reply.partial` are gone. Phone builds older than P9b are unsupported: each encrypted request and desktop stream carries `build: "p9b"`. Unmarked phones get an empty Home snapshot whose Chief chat row says “Get the latest Crewhouse app to keep chatting.”, with no `members` or real asks. `GET /api/bots/chief` returns only that sentence with a link to the current preview, so the old phone can open it. Other requests answer 426 with the notice, and desktop streams end with it. The computer’s HTTP API needs no phone marker. Every non-GET request under `/api/` requires the private `person.key` capability in `Authorization: Bearer …`, as well as `x-crewhouse: 1` for CSRF protection; desktop-control WebSockets require it in `crewhouse-person.…` as their protocol. The launcher passes it through a fragment, removed immediately into tab-local sessionStorage. No HTTP read issues authority. Pairing administration uses the same boundary; authenticated control-phone requests keep their existing rights, and view-only grants still cannot write. Shared installs must update through P1 (`bc37c20`) before this build will start.
