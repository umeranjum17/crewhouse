# The Pi flag

Pi is an engine behind `CREWHOUSE_ENGINE=pi`, off by default. `src/pi/runtime.ts` is the only file that names `@byokit/pi`, and the kit comes from a committed BYOKit ref: `node scripts/prepare-pi.mjs` builds it into `runtime/byokit` (git-ignored), so nobody without the flag fetches anything. A bot on Pi has none of Pi's own tools, since nothing in the kit passes a tool through Crewhouse's gate, and its prompt names the few it has. Its whole process runs behind bubblewrap (below), or does not run.

Several bots run side by side: each asked bot gets its own Pi process, home (`<state>/pi/<bot>`), working folder (`work/`), session and extension list. A bot nobody asked has no process. An idle Pi stops after the kit's five minutes (`CREWHOUSE_PI_IDLE_MS` changes that) and its next message picks the same session back up. Not done: the extension picker, the computer layer, the learning module, messages between machines, and Chief handing work to a helper on Pi.

## The wall

`bin/sandbox.mjs` `piWall` is the launcher `src/pi/runtime.ts` hands the kit (`BotSpec.launch`, so it runs at every start, after a crash or an idle stop too): the bot's whole Pi process behind bubblewrap. Its own user, process, ipc, uts and cgroup namespaces, no new namespaces inside, a new session, and it dies with crewd. The network stays until its own slice. No `--clearenv`: the kit builds Pi's environment from nothing, and `--setenv` would put the model key on a command line.

| Path | Inside the wall |
|---|---|
| `/usr`, and `/bin`, `/lib`, `/lib64` as links into it | read-only |
| `/etc/ssl`, `/etc/ca-certificates`, `/etc/resolv.conf`, `/etc/hosts`, `/etc/nsswitch.conf`, `/etc/localtime` | read-only, where they exist |
| the node binary, `runtime/byokit/node_modules`, the bot's extension files with `bin/pi-refusal.mjs` | read-only |
| `<state>/pi/<bot>/work` | **writable: the only place on disk the bot can change** |
| `<state>/pi/<bot>` (Pi's home) | a throwaway: Pi writes `auth.json` and `models-store.json` here and fails on a read-only home, so it is memory, gone with the process |
| `SYSTEM.md`, `settings.json`, `models.json` in that home | read-only on top of the throwaway |
| `/tmp` | a private throwaway |
| `/dev` | bubblewrap's small set |
| `/proc`, `/home`, the rest of `/etc`, the state dir, the crew dir, other bots | not there |

A write outside fails on the read-only disk (`EROFS`, or `ENOENT` where the wall leaves the parent out). `bin/pi-refusal.mjs`, loaded for every bot, turns a failed call on a path outside the folder into "That's outside my folder, so I can't open it." It only changes the words, and checks the path as written, so a link is the gate slice's. A write into Pi's home or `/tmp` reports success and vanishes with the process.

`wallDown` starts the same flags before a boot and before every job. Without bubblewrap, or with one that refuses (a stock Ubuntu 24.04 without its rule) or is too old (Ubuntu 22.04's 0.6.1 has no `--disable-userns`), the engine reports failed with one line naming the fix, a job ends on that line and Pi never starts. There is no path that runs Pi without the wall: the kit refuses to fall back, and a wall that dies at start fails the job. `CREWHOUSE_PI_TOOLS=write` turns Pi's write tool on for a proof; the product leaves it unset.

## Extensions

`src/pi/extensions.json` is the reviewed set and the default. A bot's list is `extensions.json` in its folder (`bots/<id>/`): a JSON array of reviewed names. No file means the default; `[]` means no tool, and the bot still answers in words. A bot may be able to rewrite its folder, so a list names and never points: a path, an unknown name or a broken file stops the job with the cause in the chat, and nothing it named loads. A changed list takes effect on that bot's next job.

An extension runs inside Pi and outside `Crew.gate`: the wall holds its files, but it can read the model key and reach local ports until the network slice lands, so the bar for the reviewed set is what the code can reach, not what it promises. `todo` and `hello` ship inside the pinned Pi and touch no disk, network or child process; `notes` is Crewhouse's own and touches one file. `todo` (in the default) is a working list kept in the bot's session: a helper's survives its Pi stopping and carries across its jobs, Chief's lasts one job. `hello` has no use of its own: it is there so two bots can differ. File handling and web reading are not in the set, because nothing that does them passes that bar: Pi's `read` and `write` pass no gate, and the published web and memory packages are unpinned code with the same reach. They wait for the kit's tool gate.

## Notes

`notes` (`src/pi/notes.ts`, in the default) is a bot's memory between turns, on one file, `<state>/pi/<bot>/work/notes.md`: plain markdown with one `- ` line per note, 8192 bytes at most. Pi reads it once per job, as the job starts (`before_agent_start`), and puts it at the end of that job's system prompt under "Your saved notes", marked as things the bot kept and never instructions, so a job begins knowing its notes and a note forgotten is gone from the next prompt. A note added mid-job reaches the next job's prompt, and the tool's `Saved` is all the bot needs. The tool does `add` and `forget` and has no read: a `read` is refused with no note in it. Pi starts in the bot's own folder and the file comes from that, so no input names a path and a bot reaches its own notes and no other's. A note that does not fit is not saved, and the tool says so in one line: how much is used, what the note needs, and to forget something first. It is a write outside `Crew.gate`: this code bounds what it writes, and the wall holds it to the bot's folder. A bot whose list leaves `notes` out has no notes, and turning a bot's memory off takes the tool and the prompt section away while the file stays. Full notes add 8192 bytes to each model call of a job. Nothing here is on a screen, and this is separate from what the crew knows about the person (`people/1/`, written through `crew_remember`, which Pi cannot reach). Not done: semantic search across notes, the learning module, and any sharing between bots.

## On a real model

Notes used to sit behind a `read` action on the tool. Three runs on MiniMax M3.1 Flash took 39 and 27 model calls, then 7 and 3, then 5 and 8 before the call limit stopped them, on a first ask that needs two per bot, and restart and recall were never reached. Nothing in Crewhouse, the kit or Pi repeats a read: on the scripted provider four tool rounds with no read asked for made none, and replaying the real model's calls made its four in one job, each one a call the model chose. A job began without its notes, so the tool was the only way to see them or to check a save, and the model read back after each `add`. That is why the notes now arrive with the job and the tool has no read. The next real run made no read in 20 calls, and the limit stopped it on a job this journey no longer sets: Scout was told to read Scribe's notes, which no bot can do, and it churned on `todo` until the tap refused. Neither Pi nor the kit limits calls per job (the kit's cap is its own ticket), so on this path only the bot's own answer or the task token cap ends such a job, and in this journey the tap's limit. Each real run is its own done-done record; the one for this change is named in its PR.

## Drive and witness

`node scripts/prepare-pi.mjs`, then `scripts/verify/pi-engine.sh <out-dir> <minimax-key-file>` (done-done journey `pi-engine`, with `MINIMAX_KEY_FILE` set; it spends six model calls on that key if each helper takes one call per step, and never more than `PI_CALL_LIMIT`, 20 unless set). With the flag off it runs `bot-crew` into `<out-dir>/flag-off`. With it on it boots an isolated crewd on the real pinned Pi and MiniMax M3.1 Flash, and `scripts/verify/pi-crew.mjs` drives it through the API the app uses (idle set to 8 seconds). It brings on Scout and Scribe, gives each a note, leaves Scout on the default and lists `hello` and `notes` for Scribe. It asks both at once to save a locker code in their notes, then for a word given to that helper and the colour in its own note. crewd then stops and starts again over the same folders, and both Pi sessions are removed, so `notes.md` is all that is left of the first turn. Each is asked for its own code. No bot is asked for another's: that is forbidden, so it is an assertion on the record and never a task. `scripts/verify/pi-tap.mjs` sits between crewd and the model and records each request: the job, the notes its prompt showed, everything it was sent, the tools offered, as Pi's session keeps only the calls a bot made, what each tool said, and the reply's status, finish reason, words, tool calls and tokens, so a failed run keeps its trail after the lab goes. It writes no key. Past the limit it answers an error itself and the provider is not reached, so the journey fails rather than spends more. Two Pis must be seen running at the same moment, and every Pi must stop once idle. Chief is never asked and must have no Pi folder. Any wrong word, any word of the other helper's, a model call offering anything but that helper's own tool, a tool running that is not that helper's, a helper's notes not saved, a code not recalled, a code not in the notes that job's prompt showed, the other's code or word in anything sent to the model or in a session, a job's notes changing between its rounds, or a chat whose words are not in that helper's Pi session record ends the run non-zero. Chief's own answer, a Pi killed mid-turn, the session pickup and crewd killed mid-turn are the gate's below: real Pi, scripted model.

To run it by hand: `CREWHOUSE_ENGINE=pi CREWHOUSE_ENGINE_BASE_URL=<OpenAI-compatible address> CREWHOUSE_ENGINE_API_KEY=<key> CREWHOUSE_ENGINE_MODEL=<model> ./crewhouse`. With the flag on and the kit not built, the app says what to run and stops at the engine step.

`done-done run pi-wall` (`node scripts/verify/pi-wall.mjs <out-dir>`, after `node scripts/prepare-pi.mjs`) needs no key: real Pi, scripted model, off `/tmp`. The same escape with no wall (the kit with no launcher: it lands) and with it (a real crewd: refused), then a write inside, the running launcher and mount table, a boot with no bubblewrap with the flag on and off. Its verdict is what the host sees. It writes `no-wall.txt`, `with-wall.txt`, `launcher.txt`, `mounts.txt`, `no-sandbox.txt` and `flag-off.txt`.

## Capture

`flag-off/`: the bot list and a helper's chat, as `bot-crew` writes them. `flag-on/{scout,scribe}-{390,1280}-{day,night}.png` and `flag-on/installed/{scout,scribe}-390-{day,night}.png`: each chat with its own message and answer. `crew.txt`: what was asked, the replies, the process ids, the idle checks, the tools each bot was offered, what each tool said, each `notes.md` after the restart, and job by job the model calls, notes added, reads asked for and the notes shown. Each chat ends on that helper's own code. `offered.jsonl`: the tap's own record, one line per model request. An empty list, a bot calling a tool from its own list and full notes are the gate's below, not this journey's. `pi-folder.txt`: a stand-in Pi folder, in the HOME crewd and Pi start from, hashed whole before and after. The person's real folder is not read here, so nothing in this journey proves it unchanged; that rests on the kit's own isolation test. `same-shots.txt`: any shot dropped for being byte for byte another, since done-done refuses that as reuse.

## The gate

`node scripts/test.mjs test/pi-engine.test.ts` runs real Crew and real Pi on the scripted provider: the wall (writes outside refused in the plain line, a write inside landing, a boot with bubblewrap missing, refusing or too old stopping on one line), the answer, only the default tool for the model, a forced write refused, the key off disk, and the stand-in folder unchanged; each bot's own list, neither calling the other's tool, an empty list answering in words, a working list surviving its Pi stopping, a changed list, and a path, an unknown name or a broken file stopping the job with nothing it named loaded; the notes shown once as a job starts and unchanged on its rounds, a replay of the real model's reads refused with no note in them, a note recalled in one model call once the bot's Pi has stopped and its session is gone, a path aimed at the other bot's notes landing in the bot's own, the last byte of the bound kept and the next note refused in plain words, forgetting making room, and the memory switch taking the tool and the notes away; two helpers mid-turn at once with their own process, home, notes and session, no process for one nobody asked, an idle stop and the session picked back up, and one Pi killed without touching the other (the unanswered ask stays in its session, so a real model's next reply may finish it too); and crewd killed with two helpers mid-turn, leaving no Pi behind, both jobs finishing after the restart, and a note from before the crash shown on the next job. It skips only off CI, when the kit is not built. `test/engine-seam.test.ts` pins the import guard and the runtime contract.
