# The Pi flag

Pi is an engine behind `CREWHOUSE_ENGINE=pi`, off by default. `src/pi/runtime.ts` is the only file that names `@byokit/pi`, and the kit comes from a committed BYOKit ref: `node scripts/prepare-pi.mjs` builds it into `runtime/byokit` (git-ignored), so nobody without the flag fetches anything. A bot on Pi has none of Pi's own tools, since nothing in the kit passes a tool through Crewhouse's gate, and its prompt names the few it has. Its whole process runs behind bubblewrap (below), or does not run.

Several bots run side by side: each asked bot gets its own Pi process, home (`<state>/pi/<bot>`), working folder (`work/`), session and extension list. A bot nobody asked has no process. An idle Pi stops after the kit's five minutes (`CREWHOUSE_PI_IDLE_MS` changes that) and its next message picks the same session back up. Not done: the extension picker, the computer layer, the learning module, messages between machines, and Chief handing work to a helper on Pi.

## The wall

`bin/sandbox.mjs` `piWall` is the launcher `src/pi/runtime.ts` hands the kit (`BotSpec.launch`, so it runs at every start, after a crash or an idle stop too): the bot's whole Pi process behind bubblewrap. Its own user, process, ipc, uts, cgroup and network namespaces, no new namespaces inside, a new session, and it dies with crewd. No `--clearenv`: the kit builds Pi's environment from nothing, and `--setenv` would put the model key on a command line.

| Path | Inside the wall |
|---|---|
| `/usr`, and `/bin`, `/lib`, `/lib64` as links into it | read-only |
| `/etc/ssl`, `/etc/ca-certificates`, `/etc/resolv.conf`, `/etc/hosts`, `/etc/nsswitch.conf`, `/etc/localtime` | read-only, where they exist |
| the node binary, `runtime/byokit/node_modules`, the bot's extension files with `bin/pi-refusal.mjs` and `bin/pi-door.mjs` | read-only |
| `<state>/pi/<bot>/work` | **writable: the only place on disk the bot can change** |
| `<state>/pi/<bot>` (Pi's home) | a throwaway: Pi writes `auth.json` and `models-store.json` here and fails on a read-only home, so it is memory, gone with the process |
| `SYSTEM.md`, `settings.json`, `models.json` in that home | read-only on top of the throwaway |
| `/tmp` | a private throwaway |
| `/run/crewhouse/door.sock` | the model door's socket, the one thing crewd's side of the wall offers |
| `/dev` | bubblewrap's small set |
| `/proc`, `/home`, the rest of `/etc`, the state dir, the crew dir, other bots | not there |

A write outside fails on the read-only disk (`EROFS`, or `ENOENT` where the wall leaves the parent out). `bin/pi-refusal.mjs`, loaded for every bot, turns a failed call on a path outside the folder into "That's outside my folder, so I can't open it." It only changes the words, and checks the path as written, so a link is the gate slice's. A write into Pi's home or `/tmp` reports success and vanishes with the process.

`wallDown` starts the same flags, and a real room, before a boot and before every job. Without bubblewrap, or with one that refuses (a stock Ubuntu 24.04 without its rule) or is too old (Ubuntu 22.04's 0.6.1 has no `--disable-userns`), the engine reports failed with one line naming the fix, a job ends on that line and Pi never starts. There is no path that runs Pi without the wall: the kit refuses to fall back, and a wall that dies at start fails the job. `CREWHOUSE_PI_TOOLS=write` turns Pi's write tool on for a proof; the product leaves it unset.

## The room

The launcher starts that wall inside a room: `bin/sandbox.mjs` `piRoom`, a `systemd-run --user --scope` per Pi start, so the bot stays crewd's own child and everything it starts counts against one ceiling.

**The memory ceiling is 1000 MB, with no swap** (`CEILING_MB`). A 3,911 MB computer, less the 867 MB a fresh one uses, shared by the 3 jobs crewd runs at once (`Config.maxConcurrent`), rounded down; a bot measured on a heavy page used about 850 MB. A room that reaches it dies whole (`OOMPolicy=kill`, `memory.oom.group=1`), the job ends on "This job needed more than the 1000 MB of memory a bot may use, so Crewhouse stopped it. The other bots carried on.", and the next message starts a new room on the same session. `roomFull` reads that from the manager's `oom-kill` result and clears the failed scope. The limits are read back from a real room before a boot and before every job (`wallDown`): a machine that starts the scope but applies nothing counts as no room, so does one with no login manager (a root or headless install), and the app says why in one line. Idle bots count on top of the three running jobs, the engine's own memory is unmeasured, and disk is not limited.

**Ports are the bot's own.** `--unshare-net` gives it a loopback nobody else has: two bots and this computer can hold the same port, and no address leads out. `SocketBindAllow` was the first plan and does nothing here: a user manager silently ignores it, on a scope or a service.

**The model door is the only way out** (`bin/pi-door.mjs`). Pi's `models.json` points at `127.0.0.1:3128`; the half loaded into every bot relays that port to `/run/crewhouse/door.sock`, and crewd's half (`<state>/pi/door.sock`, one per crewd, opened at the first bot) passes on `POST /v1/chat/completions` and nothing else, overwrites the authorization with the person's key and forwards to the provider's address. The key is not in the wall: `models.json` holds the words `added-at-the-door`. A bot can still spend through the door, which is the job it is there for.

**One killed process does not take the crew down.** With the flag on, each login service crewd can run in (the `crewhouse` CLI's, `packaging/launch.mjs`'s, `scripts/headless.mjs`'s) carries `OOMPolicy=continue`: the manager's default stops the whole service when any process in it is killed for memory, crewd included. Flag off, the units are what they were. A bot's room is its own scope, beside the service, so this covers what still runs inside the service: the desktops' screens and crewd's own helpers, which are outside any room.

## Extensions

`src/pi/extensions.json` is the reviewed set and the default. A bot's list is `extensions.json` in its folder (`bots/<id>/`): a JSON array of reviewed names. No file means the default; `[]` means no tool, and the bot still answers in words. A bot may be able to rewrite its folder, so a list names and never points: a path, an unknown name or a broken file stops the job with the cause in the chat, and nothing it named loads. A changed list takes effect on that bot's next job.

An extension runs inside Pi and outside `Crew.gate`: the wall and the room hold it, but it can spend through the door and read everything the bot can, so the bar for the reviewed set is what the code can reach, not what it promises. `todo` and `hello` ship inside the pinned Pi and touch no disk, network or child process; `notes` is Crewhouse's own and touches one file. `todo` (in the default) is a working list kept in the bot's session: a helper's survives its Pi stopping and carries across its jobs, Chief's lasts one job. `hello` has no use of its own: it is there so two bots can differ. File handling and web reading are not in the set, because nothing that does them passes that bar: Pi's `read` and `write` pass no gate, and the published web and memory packages are unpinned code with the same reach. They wait for the kit's tool gate.

## Notes

`notes` (`src/pi/notes.ts`, in the default) is a bot's memory between turns, on one file, `<state>/pi/<bot>/work/notes.md`: plain markdown with one `- ` line per note, 8192 bytes at most. Pi reads it once per job, as the job starts (`before_agent_start`), and puts it at the end of that job's system prompt under "Your saved notes", marked as things the bot kept and never instructions, so a job begins knowing its notes and a note forgotten is gone from the next prompt. A note added mid-job reaches the next job's prompt, and the tool's `Saved` is all the bot needs. The tool does `add` and `forget` and has no read: a `read` is refused with no note in it. Pi starts in the bot's own folder and the file comes from that, so no input names a path and a bot reaches its own notes and no other's. A note that does not fit is not saved, and the tool says so in one line: how much is used, what the note needs, and to forget something first. It is a write outside `Crew.gate`: this code bounds what it writes, and the wall holds it to the bot's folder. A bot whose list leaves `notes` out has no notes, and turning a bot's memory off takes the tool and the prompt section away while the file stays. Full notes add 8192 bytes to each model call of a job. Nothing here is on a screen, and this is separate from what the crew knows about the person (`people/1/`, written through `crew_remember`, which Pi cannot reach). Not done: semantic search across notes, the learning module, and any sharing between bots.

## Answering

A bot whose turn only calls tools is asked for its answer. The kit stops a turn past 30 tool calls (`maxToolCalls`, BYOKit's `createPiKit`, which `src/pi/runtime.ts` sets as `CALLS`). Once a turn has made 20 of them (`ASK`) and said nothing, `src/pi/runtime.ts` steers it once with "Stop calling tools now and answer the person in plain words": Pi hands that to the model after the calls in flight and before its next request, which leaves ten calls of room to answer. A model that answers ends the job in its words. One that keeps going is stopped by the kit. The kit judges the cap from Pi's output and sends its stop back, so calls already under way still run: 32 to 34 in all on a real crewd with the scripted model, which answers in milliseconds (the kit documents at most 31, and how many run on a real model's pace is unmeasured; tightening that is BYOKit's). The kit's `limit` event becomes crewd's `run.limit` event (the job, `calls`, `limit`), and the job fails on the line every stopped turn shows ("… couldn't finish this one. Try again."), never the kit's own words. A turn that says anything before its twentieth call is not asked. `done-done run pi-answer` (`node scripts/verify/pi-answer.mjs <out>`) drives all of it on a real crewd with a scripted model, and the flag off; `test/pi-engine.test.ts` holds the same journey. Not done: a real model's run, and the habit itself, which this bounds and does not fix.

## On a real model

Notes used to sit behind a `read` action on the tool. Three runs on MiniMax M3.1 Flash took 39 and 27 model calls, then 7 and 3, then 5 and 8 before the call limit stopped them, on a first ask that needs two per bot, and restart and recall were never reached. Nothing in Crewhouse, the kit or Pi repeats a read: on the scripted provider four tool rounds with no read asked for made none, and replaying the real model's calls made its four in one job, each one a call the model chose. A job began without its notes, so the tool was the only way to see them or to check a save, and the model read back after each `add`. That is why the notes now arrive with the job and the tool has no read. Three real runs followed, and none made a read. Recall was seen once: at 7 of 20 calls both bots recalled their own code after a restart with their sessions gone, but that run's record was too large for the judge, so it was never judged. It is not sealed, and on a real model this claim is not proven. In the other two the model kept calling tools instead of answering and the limit stopped it: one on a job this journey no longer sets, as Scout was told to read Scribe's notes, which no bot can do, and churned on `todo`; the last on the first ask, with both bots writing note after note. Each real run is its own done-done record, named in that change's PR. All of them predate the kit's per-turn cap and the ask for an answer (Answering, above), which no real model has run yet, so a run on this model can still end at the tap's limit.

## Drive and witness

`node scripts/prepare-pi.mjs`, then `scripts/verify/pi-engine.sh <out-dir> <minimax-key-file>` (done-done journey `pi-engine`, with `MINIMAX_KEY_FILE` set; it spends six model calls on that key if each helper takes one call per step, and never more than `PI_CALL_LIMIT`, 20 unless set). With the flag off it runs `bot-crew` into `<out-dir>/flag-off`. With it on it boots an isolated crewd on the real pinned Pi and MiniMax M3.1 Flash, and `scripts/verify/pi-crew.mjs` drives it through the API the app uses (idle set to 8 seconds). It brings on Scout and Scribe, gives each a note, leaves Scout on the default and lists `hello` and `notes` for Scribe. It asks both at once to save a locker code in their notes, then for a word given to that helper and the colour in its own note. crewd then stops and starts again over the same folders, and both Pi sessions are removed, so `notes.md` is all that is left of the first turn. Each is asked for its own code. No bot is asked for another's: that is forbidden, so it is an assertion on the record and never a task. `scripts/verify/pi-tap.mjs` sits between crewd and the model and records each request: the job, the notes its prompt showed, the tools offered, as Pi's session keeps only the calls a bot made, what each tool said, and the reply's status, finish reason, words, tool calls and tokens, and keeps everything each request sent in the lab for the separation check, as it is too long for the judge, so a failed run keeps its trail after the lab goes. It writes no key. Past the limit it answers an error itself and the provider is not reached, so the journey fails rather than spends more. Two Pis must be seen running at the same moment, and every Pi must stop once idle. Chief is never asked and must have no Pi folder. Any wrong word, any word of the other helper's, a model call offering anything but that helper's own tool, a tool running that is not that helper's, a helper's notes not saved, a code not recalled, a code not in the notes that job's prompt showed, the other's code or word in anything sent to the model or in a session, a job's notes changing between its rounds, or a chat whose words are not in that helper's Pi session record ends the run non-zero. Chief's own answer, a Pi killed mid-turn, the session pickup and crewd killed mid-turn are the gate's below: real Pi, scripted model.

`PI_SCREENS=off` leaves out the flag-off run and every screen and keeps crewd's logs in the lab, with its own step record (`pi-recall`). A spending journey only runs through `done-done verify`, whose judge reads every capture and takes 10 at most, so a real-model run sets it and leaves the screens to the scripted run.

To run it by hand: `CREWHOUSE_ENGINE=pi CREWHOUSE_ENGINE_BASE_URL=<OpenAI-compatible address> CREWHOUSE_ENGINE_API_KEY=<key> CREWHOUSE_ENGINE_MODEL=<model> ./crewhouse`. With the flag on and the kit not built, the app says what to run and stops at the engine step.

`done-done run pi-wall` (`node scripts/verify/pi-wall.mjs <out-dir>`, after `node scripts/prepare-pi.mjs`) needs no key: real Pi, scripted model, off `/tmp`. The same escape with no wall (the kit with no launcher: it lands) and with it (a real crewd: refused), then a write inside, the running launcher and mount table, a boot with no bubblewrap with the flag on and off. Its verdict is what the host sees. It writes `no-wall.txt`, `with-wall.txt`, `launcher.txt`, `mounts.txt`, `no-sandbox.txt` and `flag-off.txt`.

`done-done run pi-room` (`node scripts/verify/pi-room.mjs <out-dir>`, after `node scripts/prepare-pi.mjs`, on a login with a user manager) needs no key: real Pi, scripted model, off `/tmp`. The same endless read and the same reach with no room, then a real crewd holding two bots mid-turn while a third reaches its ceiling; two bots in rooms on one port, trying everything but the door; a real crewd in a real user service with one process killed for memory, under the manager's default and under the policy the product's own unit carries; a machine with no `systemd-run`, flag on and off. A bot on Pi has no shell (the kit leaves `bash` out), so the hog is Pi's read tool on `/dev/zero` (`CREWHOUSE_PI_TOOLS=read`) and the reach is a probe extension driven through the kit with the same `piRoom`, `piWall` and door crewd uses, since crewd loads only the reviewed list. It writes `no-room.txt`, `ceiling.txt`, `memory.txt` (each bot's numbers before and after), `door.txt`, `ports.txt`, `service.txt`, `flag-off.txt` and the step record; a failed check fails the run.

## Capture

`flag-off/`: the bot list and a helper's chat, as `bot-crew` writes them. `flag-on/{scout,scribe}-{390,1280}-{day,night}.png` and `flag-on/installed/{scout,scribe}-390-{day,night}.png`: each chat with its own message and answer. `crew.txt`: what was asked, the replies, the process ids, the idle checks, the tools each bot was offered, what each tool said, each `notes.md` after the restart, and job by job the model calls, notes added, reads asked for and the notes shown. Each chat ends on that helper's own code. `offered.jsonl`: the tap's own record, one line per model request. An empty list, a bot calling a tool from its own list and full notes are the gate's below, not this journey's. `pi-folder.txt`: a stand-in Pi folder, in the HOME crewd and Pi start from, hashed whole before and after. The person's real folder is not read here, so nothing in this journey proves it unchanged; that rests on the kit's own isolation test. `same-shots.txt`: any shot dropped for being byte for byte another, since done-done refuses that as reuse.

## The gate

`node scripts/test.mjs test/pi-engine.test.ts` runs real Crew and real Pi on the scripted provider: the room (a bot stopped at its ceiling while two others mid-turn answer, two bots on one port, the door, a machine with no manager or no limits refusing), the wall (writes outside refused in the plain line, a write inside landing, a boot with bubblewrap missing, refusing or too old stopping on one line), the answer, only the default tool for the model, a forced write refused, the key off disk, and the stand-in folder unchanged; each bot's own list, neither calling the other's tool, an empty list answering in words, a working list surviving its Pi stopping, a changed list, and a path, an unknown name or a broken file stopping the job with nothing it named loaded; the notes shown once as a job starts and unchanged on its rounds, a replay of the real model's reads refused with no note in them, a note recalled in one model call once the bot's Pi has stopped and its session is gone, a path aimed at the other bot's notes landing in the bot's own, the last byte of the bound kept and the next note refused in plain words, forgetting making room, and the memory switch taking the tool and the notes away; a bot that only calls tools asked once for its answer and answering inside the cap, one that keeps going ending on the stopped-turn line with a run.limit event, and a plain turn never asked; two helpers mid-turn at once with their own process, home, notes and session, no process for one nobody asked, an idle stop and the session picked back up, and one Pi killed without touching the other (the unanswered ask stays in its session, so a real model's next reply may finish it too); and crewd killed with two helpers mid-turn, leaving no Pi behind, both jobs finishing after the restart, and a note from before the crash shown on the next job. It skips only off CI, when the kit is not built. `test/engine-seam.test.ts` pins the import guard and the runtime contract.
