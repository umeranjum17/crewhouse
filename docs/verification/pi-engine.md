# The Pi flag

Pi is an engine behind `CREWHOUSE_ENGINE=pi`, off by default. `src/pi/runtime.ts` is the only file that names `@byokit/pi`, and the kit comes from a committed BYOKit ref: `node scripts/prepare-pi.mjs` builds it into `runtime/byokit` (git-ignored), so nobody without the flag fetches anything. A bot on Pi has none of Pi's own tools, since nothing in the kit passes a tool through Crewhouse's gate, and its prompt names the few it has.

Several bots run side by side: each asked bot gets its own Pi process, home (`<state>/pi/<bot>`), working folder (`work/`), session and extension list. A bot nobody asked has no process. An idle Pi stops after the kit's five minutes (`CREWHOUSE_PI_IDLE_MS` changes that) and its next message picks the same session back up. Pi has no OS sandbox: what keeps one bot out of another's folder is that neither has a tool that reaches a folder. Not done: the extension picker, the computer layer, the learning module, messages between machines, and Chief handing work to a helper on Pi.

## Extensions

`src/pi/extensions.json` is the reviewed set and the default. A bot's list is `extensions.json` in its folder (`bots/<id>/`): a JSON array of reviewed names. No file means the default; `[]` means no tool, and the bot still answers in words. A bot may be able to rewrite its folder, so a list names and never points: a path, an unknown name or a broken file stops the job with the cause in the chat, and nothing it named loads. A changed list takes effect on that bot's next job.

An extension runs inside Pi with the person's own rights and outside `Crew.gate`, so the bar for the reviewed set is what the code can reach, not what it promises. Both entries ship inside the pinned Pi and touch no disk, network or child process. `todo` (the default) is a working list kept in the bot's session: a helper's survives its Pi stopping and carries across its jobs, Chief's lasts one job. `hello` has no use of its own: it is there so two bots can differ. Memory notes, file handling and web reading are not in the set, because nothing that does them passes that bar: Pi's `read` and `write` reach every folder the person can, and the published web and memory packages are unpinned code with the same rights. They wait for the kit's tool gate.

## Drive and witness

`node scripts/prepare-pi.mjs`, then `scripts/verify/pi-engine.sh <out-dir> <minimax-key-file>` (done-done journey `pi-engine`, with `MINIMAX_KEY_FILE` set; it spends a few model calls on that key). With the flag off it runs `bot-crew` into `<out-dir>/flag-off`. With it on it boots an isolated crewd on the real pinned Pi and MiniMax M3.1 Flash, and `scripts/verify/pi-crew.mjs` drives it through the API the app uses (idle set to 8 seconds). It brings on Scout, Scribe and Reel, gives Scout and Scribe a note each, leaves Scout on the default, lists `hello` for Scribe and nothing for Reel. It asks Scout and Scribe at once to use their own tool, then for a word given to that helper and the colour in its own note, then asks Reel a plain question: about five model calls. `scripts/verify/pi-tap.mjs` sits between crewd and the model and records the tools each request offered, as Pi's session keeps only the calls a bot made; it writes no key and no words. Two Pis must be seen running at the same moment, and every Pi must stop once idle. Chief is never asked and must have no Pi folder. Any wrong word, any word of the other helper's, a model call offering anything but that helper's own tool, a helper not calling its tool, or a chat whose words are not in that helper's Pi session record ends the run non-zero. Chief's own answer, a Pi killed mid-turn, the session pickup and crewd's restart are the gate's below: real Pi, scripted model.

To run it by hand: `CREWHOUSE_ENGINE=pi CREWHOUSE_ENGINE_BASE_URL=<OpenAI-compatible address> CREWHOUSE_ENGINE_API_KEY=<key> CREWHOUSE_ENGINE_MODEL=<model> ./crewhouse`. With the flag on and the kit not built, the app says what to run and stops at the engine step.

## Capture

`flag-off/`: the bot list and a helper's chat, as `bot-crew` writes them. `flag-on/{scout,scribe,reel}-{390,1280}-{day,night}.png` and `flag-on/installed/{scout,scribe,reel}-390-{day,night}.png`: each chat with its own message and answer. `crew.txt`: what was asked, the replies, the process ids, the idle checks, the tools each bot was offered and what each tool said. `offered.jsonl`: the tap's own record, one line per model request. `pi-folder.txt`: a stand-in Pi folder, in the HOME crewd and Pi start from, hashed whole before and after. The person's real folder is not read here, so nothing in this journey proves it unchanged; that rests on the kit's own isolation test. `same-shots.txt`: any shot dropped for being byte for byte another, since done-done refuses that as reuse.

## The gate

`node scripts/test.mjs test/pi-engine.test.ts` runs real Crew and real Pi on the scripted provider: the answer, only the default tool for the model, a forced write refused, the key off disk, and the stand-in folder unchanged; each bot's own list, neither calling the other's tool, an empty list answering in words, a working list surviving its Pi stopping, a changed list, and a path, an unknown name or a broken file stopping the job with nothing it named loaded; two helpers mid-turn at once with their own process, home, notes and session, no process for one nobody asked, an idle stop and the session picked back up, and one Pi killed without touching the other (the unanswered ask stays in its session, so a real model's next reply may finish it too); and crewd killed with two helpers mid-turn, leaving no Pi behind, both jobs finishing after the restart. It skips only off CI, when the kit is not built. `test/engine-seam.test.ts` pins the import guard and the runtime contract.
